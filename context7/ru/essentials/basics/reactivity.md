# Введение в реактивность

До сих пор мы рассмотрели, как декларировать статические пользовательские интерфейсы с помощью RSX. Теперь пришло время сделать наш UI интерактивным. Когда пользователь нажимает кнопку, перемещает курсор или вводит текст, мы хотим обновлять наш UI в ответ.

Акт реагирования на изменения состояния называется *реактивностью*. Реактивность лежит в самом сердце Dioxus. Все — от загрузки данных до маршрутизации — построено вокруг реагирования на изменения состояния.

Аналогично библиотекам вроде ReactJS, Dioxus предоставляет встроенную систему реактивности, избавляя вас от необходимости вручную ставить в очередь перерисовки компонентов. Если вы пришли из веб-разработки, это должно показаться знакомым. Если у вас в основном опыт с immediate-mode GUI, это может показаться чуждым.

Системы реактивности позволяют создавать более крупные, более модульные, сложные GUI, чем это обычно достижимо с другими подходами. Чтобы создавать UI, которые эффективно используют реактивность, мы следуем трем основным столпам:

- **Данные текут вниз**: Наши приложения поддерживают однонаправленный поток данных от родителей к детям
- **Данные отслеживаются**: Модификации данных наблюдаются реактивными областями и побочными эффектами
- **Данные выводятся**: Наш UI и состояние являются чистой функцией наших источников данных

## Столп 1: Данные текут вниз

Первый фундаментальный столп реактивности: данные текут вниз. По мере роста наших приложений растет и их сложность. В приложениях с десятками экранов и сотнями компонентов может стать сложно рассуждать об отношениях между родительскими и дочерними элементами. Обеспечивая однонаправленный поток данных через наше приложение, мы можем быть уверены, что дочерний компонент рендерится *чисто* как функция своих входных данных.

Чтобы сделать наши приложения интерактивными, мы следуем похожему паттерну. Компоненты предоставляют два элемента: *значения* и *функции* для модификации этих значений. Эти элементы передаются *вниз* по дереву как свойства. Dioxus не предоставляет способа для дочерних компонентов "дотянуться" и модифицировать состояние родителя.

Функции, которые мы передаем вниз по дереву, могут свободно мутировать состояние в *текущем* компоненте. Однако дочерний компонент не может *напрямую* модифицировать состояние своего родителя. Это гарантирует, что все мутации состояния определены в **той же области, что и само состояние**, упрощая рассуждение о состоянии нашего приложения в масштабе.

## Столп 2: Данные отслеживаются

Второй фундаментальный столп реактивности: данные отслеживаются. Когда вы используете различные примитивы состояния в Dioxus, рантайм Dioxus *отслеживает* изменения базового значения. Всякий раз, когда вы вызываете `.set()` или `.write()` на *реактивном значении*, эта операция *наблюдается* и запускаются *эффекты*.

Основным реактивным значением в Dioxus является сигнал. Когда сигналы используются в *реактивных контекстах*, их связанные *чтения* и *записи* отслеживаются. Каждый компонент является реактивным контекстом. Всякий раз, когда значение сигнала модифицируется, в очередь ставится *побочный эффект*, который перезапускает любые реактивные контексты, которые прочитали значение сигнала.

```rust
#[component]
fn Filter() -> Element {
    let mut selection = use_signal(|| "none");

    rsx! {
        // чтение значения *selection* имеет побочный эффект перерисовки этого компонента
        div { "{selection}" }

        // Вызов `.set()` запускает побочные эффекты
        button { onclick: move |_| selection.set("dogs"), "Установить фильтр" }
    }
}
```

Многие хуки используют реактивные контексты для прикрепления своих собственных побочных эффектов.

## Столп 3: Данные выводятся

Третий столп реактивности: значения *выводятся*. После любого изменения состояния в нашем приложении мы хотим, чтобы UI соответствовал тому, что мы декларировали в нашем RSX. В этом случае UI *выводится* из состояния нашего приложения. Аналогично, в реактивном программировании все данные либо являются источником, либо *выводятся* из источника.

При рендеринге компонентов мы поэтому предпочитаем выполнять любые трансформации данных во время рендеринга или в мемо. Мы *не* модифицируем данные во время рендеринга.

```rust
// ✅ *num_names* выводится из "names"
let names = use_signal(|| vec!["Jane", "Jack", "Jill"]);

rsx! {
    // производное значение
    "Количество имен: {names.len()}"
}
```
