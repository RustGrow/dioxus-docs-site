# Глобальный Контекст

К настоящему моменту у вас есть необходимые знания для создания больших приложений на Dioxus! Когда дерево компонентов вырастает до нескольких уровней вложенности, передача состояния через пропсы компонентов может стать утомительной и repetitive.

```rust
fn app() -> Element {
    let name = use_signal(|| "bob".to_string());
    rsx! { Container { name } }
}

#[name]
fn Container(name: Signal<String>) -> Element {
    rsx! { Content { name } }
}

#[name]
fn Content(name: Signal<String>) -> Element {
    rsx! { Title { name } }
}

#[name]
fn Title(name: Signal<String>) -> Element {
    rsx! { h1 { "{name}" } }
}
```

Передача состояния через несколько уровней свойств компонентов называется "prop drilling". Не было бы здорово, если бы мы могли передать сигнал `name` из корня приложения *напрямую* компоненту Title?

Здесь на помощь приходит *глобальный контекст*. Компоненты могут вставлять значения в глобальный контекст, позволяя любым дочерним компонентам "дотянуться" вверх и прочитать эти значения.

![Дерево Контекста](/assets/07/context-tree.png)

Обратите внимание, что контекст доступен только при "достижении вверх" по дереву. Вспомните фундаментальный столп реактивности: данные текут вниз. В модели однонаправленного потока данных дочерние компоненты могут свободно читать состояние родительских компонентов. Вы можете думать о контексте как о невидимом дополнительном аргументе, передаваемом через свойства каждого компонента от корня к каждому дочернему.

```rust
fn Child(context: Context, ..props) -> Element { /* */ }
```

Контекст примерно определяется как рекурсивное определение самого себя:

```rust
struct Context {
    contexts: Vec<Rc<dyn Any>>
    parent: Option<Context>,
}
```

Когда мы "достигаем вверх" по дереву, мы сначала проходим по списку контекстов текущего компонента, а затем рекурсивно проверяем каждого родителя, пока не найдем целевой контекст.

## Сравнение Способов Передачи Состояния

Dioxus предоставляет три разных способа передачи состояния между компонентами. Контекст — это лишь один из них:

1. **Передача значений через пропсы** — самый явный и локальный подход. Используйте его, когда не слишком утомительно передавать значение через несколько уровней.

2. **Использование контекста** — отлично подходит для состояния, которое является глобальным для поддерева вашего приложения. Он позволяет создавать несколько "почти глобальных" состояний, при этом сохраняя различное состояние при повторном использовании компонентов.

3. **Использование глобальных сигналов** — очень эргономично, если ваше состояние действительно глобально, но не стоит использовать их, если состояние должно отличаться для разных экземпляров компонента. Библиотекам следует избегать глобальных сигналов, чтобы компоненты были более переиспользуемыми.

Остальная часть этой страницы посвящена контексту. О глобальных сигналах см. раздел [Глобальные Сигналы](#глобальные-сигналы) внизу этой страницы.

## Предоставление и Потребление Контекста

Прежде чем мы сможем начать достигать вверх по дереву компонентов, нам сначала нужно *предоставить* контекст дочерним компонентам. Dioxus предоставляет функции `provide_context` и `use_context_provider`. Обычно вы размещаете инициализатор состояния в хуке `use_context_provider` следующим образом:

```rust
fn app() -> Element {
    // use_context_provider принимает замыкающую функцию-инициализатор
    use_context_provider(|| "Hello world!".to_string());

    rsx! { Child {} }
}
```

Теперь, чтобы прочитать контекст, мы сопоставляем провайдер с потребителем. Для этого вызываем `use_context` и устанавливаем возвращаемый тип таким же, как тип предоставленного контекста. В примере выше мы предоставили объект типа `String`; следовательно, потребляем его с помощью дженерика `String`:

```rust
fn Child() -> Element {
    let title = use_context::<String>();
    rsx! { "{title}" }
}
```

Синтаксис `::<String>` объявляет возвращаемый тип для этого использования `use_context`. В Dioxus объекты контекста индексируются по их [TypeId](https://doc.rust-lang.org/std/any/struct.TypeId.html). TypeId типа — это хеш времени компиляции, который уникально идентифицирует каждый тип Rust. Никакие два типа не будут иметь одинаковый TypeId, если только они не относятся к одному и тому же базовому объявлению типа — то есть [псевдонимы типов](https://doc.rust-lang.org/reference/items/type-aliases.html) будут иметь одинаковый TypeId.

При предоставлении объектов контекста мы должны обернуть данные, которые хотим сохранить, в пользовательский тип или [new type](https://doc.rust-lang.org/rust-by-example/generics/new_types.html). Это гарантирует, что мы можем хранить несколько объектов `String` в дереве контекстов и извлекать их по типу обертки.

Объявление нового типа требует объявления новой структуры:

```rust
#[derive(Clone)]
struct Title(String);

#[derive(Clone)]
struct Subtitle(String);
```

Затем мы можем предоставить контекст, используя наши типы-обертки:

```rust
use_context_provider(|| Title("Hello world!".to_string()));
use_context_provider(|| Subtitle("Hello world!".to_string()));
```

Чтобы потребить контекст, мы передаем соответствующий тип структуры:
```rust
let title = use_context::<Title>();
let subtitle = use_context::<Subtitle>();
```

На практике вам не нужно оборачивать *каждое* поле вашего состояния в newtype, обычно достаточно одной структуры для инкапсуляции набора данных.

```rust
#[derive(Clone)]
struct HeaderContext {
    title: String,
    subtitle: String
}
```

## Компоненты-Провайдеры Контекста

Иногда вы не хотите, чтобы контекст применялся ко *всем* компонентам в вашем дереве — достаточно лишь подмножества. Если вы хотите предоставить состояние ограниченной части элементов в макросе `rsx!`, вы можете создать новый компонент, который предоставляет контекст своим дочерним элементам, называемый **Context Provider** (провайдер контекста).

Например, мы можем написать компонент `ThemeProvider`, который оборачивает дочерние элементы и предоставляет контекст:

```rust
#[component]
fn ThemeProvider(children: Element, color: ThemeColor) -> Element {
    use_context_provider(|| ThemeState::new(color));
    children
}
```

Затем мы можем использовать провайдер контекста в нашем RSX несколько раз, но с разными параметрами:

```rust
fn app() -> Element {
    rsx! {
        ThemeProvider {
            color: ThemeColor::Red,
            h1 { "Red theme!" }
        }
        ThemeProvider {
            color: ThemeColor::Blue,
            h1 { "Blue theme!" }
        }
    }
}
```

## Динамическое Предоставление и Потребление Контекста

Dioxus предоставляет несколько различных функций для предоставления и потребления контекста. Вам не обязательно использовать хуки `use_context` и `use_context_provider`. Вместо этого вы можете динамически предоставлять и потреблять контекст *во время выполнения* с помощью `provide_context` и `consume_context`.

Возможность динамически потреблять контекст очень мощна. Мы можем напрямую обращаться к контексту в обработчиках событий и асинхронных задачах без дополнительного хука.

```rust
fn ToggleTheme() -> Element {
    // хуки не требуются!
    rsx! {
        button {
            onclick: move |_| consume_context::<ThemeProvider>().set_theme(ThemeColor::Red),
            "Make Red"
        }
        button {
            onclick: move |_| consume_context::<ThemeProvider>().set_theme(ThemeColor::Blue),
            "Make Blue"
        }
    }
}
```

Поскольку рантайм Dioxus всегда устанавливает контекст темы при выполнении обработчиков и опросе futures, это даже работает в асинхронных задачах:

```rust
rsx! {
    button {
        onclick: move |_| async move {
            let color = fetch_random_color().await;
            consume_context::<ThemeProvider>().set_theme(color);
        },
        "Make Random Color"
    }
}
```

Обратите внимание, что мы также можем динамически предоставлять контекст, хотя это менее полезно. Всякий раз, когда мы динамически предоставляем контекст, запись контекста текущего компонента заменяется (если она существовала).

```rust
use_context_provider(|| ThemeProvider::new());
rsx! {
    button {
        onclick: move |_| dioxus::core::provide_context(ThemeProvider::reset()),
        "Reset Theme Provider"
    }
}
```

Замена контекста *не* является реактивной операцией, что по сути ограничивает ее полезность.

## Предоставление Сигналов

До сих пор мы демонстрировали только предоставление простых значений, таких как Strings. Как упоминалось выше, динамическая замена контекста не является реактивной операцией, поэтому мы не должны использовать ее для обновления состояния в нашем приложении.

Чтобы сделать наш контекст полностью реактивным, мы должны предоставлять сигналы. Обычно вы объединяете коллекцию сигналов вместе в более крупный объект состояния:

```rust
#[derive(Clone, Copy)]
struct HeaderContext {
    title: Signal<String>,
    subtitle: Signal<String>
}
```

Обратите внимание, что наш `HeaderContext` реализует как `Clone`, так и `Copy`. Чтобы контекст можно было разделять по всему дереву компонентов, каждая запись контекста должна реализовывать `Clone`. Сигналы Dioxus чрезвычайно удобны, потому что они также реализуют `Copy`, что упрощает работу с ними в асинхронных контекстах. Аналогично, наши пользовательские структуры контекста также могут реализовывать `Copy` и получить те же эргономические преимущества.

Чтобы сконструировать наш HeaderContext, мы используем один из двух подходов. Первый — построить компонент-провайдер:

```rust
#[component]
fn HeaderProvider(children: Element) -> Element {
    // создаем сигналы с помощью `use_signal`
    let title = use_signal(|| "Title".to_string());
    let subtitle = use_signal(|| "Subtitle".to_string());

    // А затем используем их для прямого построения HeaderContext
    use_context_provider(|| HeaderContext { title, subtitle });

    children
}
```

Второй подход — использовать `Signal::new()` напрямую, либо в методе `HeaderContext::new()`, либо в функции `use_header_provider`. Преимущество здесь в том, что пользователи могут предоставить `HeaderContext`, не оборачивая свои RSX-элементы.

```rust
fn app() -> Element {
    use_context_provider(|| HeaderContext::new());

    ...
}

impl HeaderContext {
    fn new() -> HeaderContext {
        HeaderContext {
            title: Signal::new("Title")
            subtitle: Signal::new("Subtitle")
        }
    }
}
```

Использование методов `new` — это идиоматичный Rust и позволяет нам настраивать начальные параметры, используемые для построения контекста.

Когда мы объединяем сигналы в структуру, мы можем немного упростить работу с состоянием, добавив методы доступа и изменения.

```rust
impl HeaderContext {
    pub fn reset(&mut self) {
        self.title.set("".to_string());
        self.subtitle.set("".to_string());
    }

    pub async fn fetch(&mut self) {
        let data = api::fetch_header_info().await;
        self.title.set(data.title);
        self.subtitle.set(data.subtitle);
    }

    pub fn uppercase_title(&self) -> String {
        self.title.cloned().to_ascii_uppercase()
    }
}
```

Теперь, когда мы хотим взаимодействовать с контекстом заголовка, мы используем его методы:

```rust
let mut header = use_context::<HeaderContext>();

rsx! {
    h1 { "{header.uppercase_title()}" }
    button { onclick: move |_| header.reset(), "Reset" }
    button { onclick: move |_| header.fetch(), "Fetch New" }
}
```

С контекстом и сигналами у вас должны быть все инструменты, необходимые для проектирования больших реактивных приложений на Dioxus. Эти простые примитивы составляют полное решение для управления состоянием от первой стороны. Можно попрощаться с библиотеками вроде [Redux](https://redux.js.org) и [Mobx](https://mobx.js.org/README.html)!

## Глобальные Сигналы

С глобальным состоянием мы еще *не совсем* закончили! Dioxus предоставляет улучшение паттерна "сигналы в контексте" с помощью **глобальных сигналов**. Глобальные сигналы доступны *каждому* компоненту в вашем приложении. Глобальные сигналы автоматически монтируются к корневому компоненту вашего приложения.

Поскольку `GlobalSignalProvider` автоматически монтируется к вашему приложению, вам не нужно вызывать `use_context_provider`. Чтобы создать новый глобальный сигнал, используйте инициализатор `Signal::global` в `static`.

```rust
static SONG: GlobalSignal<String> = Signal::global(|| "Drift Away".to_string());
```

А затем читайте и пишите в него из любого места:

```rust
#[component]
    fn Player() -> Element {
        rsx! {
            h3 { "Now playing {SONG}" }
            button {
                onclick: move |_| *SONG.write() = "Vienna".to_string(),
                "Shuffle"
            }
        }
    }
```

GlobalSignals являются глобальными только для одного приложения — не для всей программы. Это означает, что в "мультитенантных" окружениях, таких как серверный рендеринг (SSR) и многооконный десктоп, каждое приложение получает свое *независимое* значение глобального сигнала.

```rust
// каждый отдельный экземпляр приложения получает свое собственное значение GlobalSignal "COUNT"
static COUNT: GlobalSignal<i32> = Signal::global(|| 0);

fn app() -> Element {
    rsx! {
        div { "{COUNT}" }
        button { onclick: move |_| *COUNT.write() += 1 }
    }
}
```

Хотя может показаться, что `COUNT` синхронизируется между *всеми* запущенными приложениями, на самом деле он локален только для одного приложения за раз. Глобальные сигналы примерно реализованы как HashMap ключа глобального сигнала к значению, где ключ — это уникальный идентификатор времени компиляции для каждого экземпляра.

Помимо глобальных сигналов, у вас также могут быть глобальные мемо с GlobalMemo. Они похожи на обычные мемо, позволяя вам инкрементально вычислять новые значения по мере обновления внутренних реактивных значений.

```rust
static COUNT: GlobalSignal<i32> = Signal::global(|| 0);
static DOUBLE_COUNT: GlobalMemo<i32> = Memo::global(|| COUNT.cloned() * 2);

fn app() -> Element {
    rsx! {
        div { "count: {COUNT}" }
        div { "double: {DOUBLE_COUNT}" }
        button { onclick: move |_| *COUNT.write() += 1 }
    }
}
```

Обратите внимание, что типы GlobalSignal и GlobalMemo на самом деле являются `Global<Signal<T>>` и `Global<Memo<T>>` — если вы реализуете необходимые трейты, вы можете сделать любой пользовательский реактивный тип глобально доступным!
