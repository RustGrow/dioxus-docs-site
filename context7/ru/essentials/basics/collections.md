# Реактивные Хранилища и Коллекции

Объект `Signal` отлично подходит для создания реактивного состояния вашего приложения. До сих пор мы демонстрировали, как сигналы могут сделать реактивным любой тип, просто обернув его инициализатор в хук `use_signal`:

```rust
let mut count: Signal<i32> = use_signal(|| 0);
```

Всякий раз, когда мы вызываем `.read()` или `.write()` на сигнале, мы можем легко получить доступ и изменить базовое значение, а также поставить компоненты в очередь на повторный рендеринг.

По мере эволюции ваших структур данных вы можете столкнуться с новыми проблемами. Некоторые вопросы, которые могут возникнуть:

- "Как добавить реактивность к типам, которыми я не владею?"
- "Что именно перерендеривается, когда я изменяю только *одну* запись в коллекции?"
- "Что если я не могу обернуть каждое значение в моем приложении в сигнал?"

По мере того как наши приложения становятся интереснее, мы чаще используем сторонние библиотеки и организуем наше состояние в коллекции вроде HashMaps, BTrees и Vectors. В этих случаях нам нужно взаимодействовать со структурами данных, *которыми мы не владеем*.

Чтобы упростить работу со структурами и коллекциями, Dioxus предоставляет **Store** (Хранилище).

## Реактивные Хранилища

В Dioxus реактивные хранилища — это типы, которые изолируют реактивность только на путь в структуре данных. Хранилища позволяют нам "приближаться" к меньшей части наших данных, игнорируя все остальные чтения и записи.

Простейшие хранилища — это структуры, для которых выводится трейт `Store`:

```rust
#[derive(Store)]
struct HeaderState {
    title: String,
    subtitle: String
}
```

Чтобы использовать хранилища как состояние, мы используем хук `use_store`:

```rust
let header = use_store(|| HeaderState {
    title: "Hello, ".to_string(),
    subtitle: "world!".to_string(),
});
```

Производный макрос `Store` генерирует дополнительные методы на `Store<HeaderState>`, которые позволяют нам "приближаться" к полям структуры. Мы получаем доступ к полям, вызывая имя поля как метод:

```rust
fn app() -> Element {
    let header = use_store(|| HeaderState {
        title: "Hello, ".to_string(),
        subtitle: "world!".to_string(),
    });

    // мы можем "приблизиться" с помощью сгенерированного метода `.title()`.
    let title = header.title();

    rsx! { "{title}" }
}
```

Метод `.title()` возвращает объект, называемый "lens" (линза). Линзы не уникальны для Dioxus — они распространены в функциональном программировании и веб-разработке.

### Тип `Store<Value, Lens>`

Когда мы используем метод `.title()`, мы создаем новый объект `Store`, но с дополнительным дженерик-параметром, который указывает, как линза "приближается" к нашему состоянию. Линзы являются zero-cost, что означает, что стоимость использования метода `.title()` такая же, как прямое индексирование структуры через `.title`. Одним из побочных эффектов является то, что дженерик-тип не может быть явно "назван" или указан:

```rust
// второй дженерик — это уникальный тип линзы
let title: Store<HeaderState, _> = header.title();
```

Обратите внимание, как у стандартного `Store`, который мы получаем от `use_store`, есть опущенный дженерик-аргумент по умолчанию:

```rust
let title: Store<HeaderState> = use_store(|| HeaderState::new());
```

Поскольку линза "неименуема", нам нужно принимать линзу как дженерик в любых функциях, работающих с хранилищами. Если нам нужно только читать из хранилища, мы можем требовать, чтобы линза реализовывала трейт `Readable`. Если нам нужно писать в хранилище, мы можем требовать, чтобы линза реализовывала трейт `Writable`.

```rust
// Эта функция работает с любой линзой, которая может читать состояние заголовка, например ReadStore<HeaderState> или Store<HeaderState, _>
fn get_title(state: Store<HeaderState, impl Readable<Target = HeaderState>>) -> String {
    state.title().cloned()
}

// Эта функция работает с любой линзой, которая может писать в состояние заголовка, например Store<HeaderState> или Store<HeaderState, _>
fn clear_title(state: Store<HeaderState, impl Writable<Target = HeaderState>>) {
    state.title().take();
}
```

На границе компонента Хранилища автоматически упаковываются и преобразуются в `ReadSignal` или `ReadStore` по мере необходимости, так что вам не нужно беспокоиться о типе линзы:

```rust
fn app() -> Element {
    let header = use_store(|| HeaderState {
        title: "Hello, ".to_string(),
        subtitle: "world!".to_string(),
    });

    rsx! {
        // линза, возвращенная `.title()`, автоматически преобразуется в `ReadSignal`!
        Title { title: header.title() }
        // линза, возвращенная `.subtitle()`, автоматически преобразуется в `ReadStore`!
        Subtitle { subtitle: header.subtitle() }
    }
}

#[component]
fn Title(title: ReadSignal<String>) -> Element {
    ..
}

#[component]
fn Subtitle(subtitle: ReadStore<String>) -> Element {
    ..
}
```

### Хранилища Readable и Writable

Тип `Store` реализует те же трейты `Readable` и `Writable`, что и сигналы, позволяя нам использовать хранилища и линзы так же, как сигналы:

```rust
// мы можем использовать `.read()`
let title = header.title().read();

// мы можем использовать `.write()`
*header.title().write() = "goodbye".to_string();

// мы можем использовать `.set()`
header.title().set("goodbye!".to_string());
```

Хранилища и линзы также реализуют те же расширяющие трейты `Readable` и `Writable`, позволяя нам работать с ними как с обычными значениями Rust:

```rust
fn app() -> Element {
    let mut header = use_store(|| HeaderState {
        title: "Hello, ".to_string(),
        subtitle: "world!".to_string(),
    });

    rsx! {
        // Хранилища реализуют Display
        h3 { "{header.title()}" }

        // Они `Copy`, что упрощает совместное использование между скоупами
        button { onclick: move |_| header.title().write().clear() }
    }
}
```

### Вложенные Хранилища

Хранилища также могут быть вложенными, позволяя линзам "просматривать" несколько уровней структур данных:

```rust
#[derive(Store)]
struct HeaderState {
    title: String,
    subtitle: String,
    other: OtherHeaderState,
}

#[derive(Store)]
struct OtherHeaderState {
    title2: String,
    subtitle2: String,
}

// теперь мы можем "приблизиться" к вложенным полям:
let title2 = header.other().title2();
```

Способность хранилища "приближаться" через вложенные структуры данных зависит от того, реализуют ли типы трейт `Store`. Если, например, вложенные структуры *не* реализуют трейт `Store`, то мы не можем создавать для них линзы:

```rust
#[derive(Store)]
struct HeaderState {
    title: String,
    subtitle: String,
    other: OtherHeaderState,
}

struct OtherHeaderState {
    title2: String,
    subtitle2: String,
}

// ❌ мы *не можем* создать линзу для OtherHeaderState
let title2 = header.other().title2();
```

Важно знать, что хранилища не могут создавать линзы через типы, не реализующие `Store`. При работе со сторонними API и структурами данных внешние структуры обычно не реализуют трейт `Store`, что означает, что мы не можем сделать их полностью реактивными.

### Result, Option и перечисляемые Линзы

Некоторые поля нашего хранилища могут быть перечисляемыми значениями, такими как [Result](https://doc.rust-lang.org/std/result/) или [Option](https://doc.rust-lang.org/std/option/). Хранилища предоставляют несколько полезных вспомогательных методов, которые упрощают работу с перечислением и делают само перечисление реактивным.

Мы можем обновить наш пример заголовка, чтобы включить типы `Result` и `Option`:

```rust
#[derive(Store)]
struct HeaderState {
    title: Result<String, String>,
    subtitle: Option<String>,
}
```

Как и обычные `Result` и `Option`, линзы хранилищ также реализуют `.unwrap()` (и ряд вспомогательных методов).

```rust
let title = header.title().unwrap();
let subtitle = header.subtitle().unwrap();
```

Чтобы правильно получить доступ к базовому `Option<String>`, мы можем использовать один из двух подходов:

- Метод `.transpose()`, который преобразует `Store<Option<String>>` в `Option<Store<String>>`
- Использование `.read().as_ref()`

Подход `.transpose()` полезен, так как мы сохраняем линзу, позволяя нам "приближаться" к вложенным структурам и коллекциям.

```rust
let len = match header.subtitle().transpose() {
    Some(subtitle) => subtitle.read().len(),
    None => 0,
};
```

Альтернативно, мы можем использовать `.as_ref()` на линзе, чтобы получить доступ к базовому значению, но мы теряем возможность реактивно "приближаться" дальше:

```rust
let len = match header.subtitle().as_ref() {
    Some(subtitle) => subtitle.chars().count(),
    None => 0,
};
```

Обычно вы можете выбрать любой подход — просто знайте, что использование `.as_ref()` внутренне вызывает `.read()`, и "реактивное приближение" может быть не идеально точным.

### Гранулярные Подписки с Вложенными Хранилищами

Одно из ключевых преимуществ хранилищ заключается в том, что они лениво создают сигналы для каждого поля и элемента коллекции. Это означает, что изменение одного поля или добавление элемента в вектор приведёт к перерисовке только тех частей приложения, которые фактически зависят от этого конкретного фрагмента данных.

Вот более сложный пример, демонстрирующий хранилища с рекурсивной древовидной структурой:

```rust
#[derive(Store, Default)]
struct CounterTree {
    count: i32,
    children: Vec<CounterTree>,
}

fn app() -> Element {
    let value = use_store(Default::default);

    rsx! {
        Tree { value }
    }
}

#[component]
fn Tree(value: Store<CounterTree>) -> Element {
    // Вызов сгенерированного метода `count` возвращает новое хранилище, ограниченное только полем count
    let mut count = value.count();
    let mut children = value.children();

    rsx! {
        button {
            // Увеличение счетчика приведет к перезапуску только тех частей приложения, которые читали поле count
            onclick: move |_| count += 1,
            "Увеличить"
        }
        button {
            // Хранилища знают о структурах данных вроде Vec и HashMap. Когда мы добавляем элемент,
            // перезапустятся только те части приложения, которые зависят от длины вектора
            onclick: move |_| children.push(Default::default()),
            "Добавить дочерний"
        }
        ul {
            // Итерация по дочерним элементам дает нам хранилища, ограниченные каждым дочерним элементом
            for value in children.iter() {
                li {
                    Tree { value }
                }
            }
        }
    }
}
```

В этом примере нажатие "Увеличить" перерисовывает только отображение счётчика для этого конкретного узла дерева, но не его дочерние или соседние элементы. Нажатие "Добавить дочерний" обновляет только список дочерних элементов без перерисовки существующих дочерних компонентов. Такая гранулярная реактивность особенно мощна для больших вложенных структур данных.

## Реактивные Коллекции

Вы можете задаться вопросом: "как лучше всего обрабатывать HashMaps и Vectors в сигналах?" До сих пор мы демонстрировали только простое состояние в сигналах, такое как строки и целые числа. Так же, как строки и целые числа, вы можете помещать коллекции непосредственно в сигналы:

```rust
type UserId = i32;
struct UserData {
    name: String,
    email: String,
}

let mut users = use_signal(|| HashMap::<UserId, UserData>::new());

rsx! {
    ul {
        for (id, data) in users.read().iter() {
            li { key: "{id}", "{data.name}" }
        }
    }
}
```

Для небольших приложений это обычно нормально. Однако в конечном итоге мы можем захотеть вынести элемент `li {}` в отдельный компонент. К сожалению, мы сразу столкнемся с проблемами времени жизни с гвардом `GenerationalRef`, возвращенным `.iter()`:

```rust
// ❌ Это не скомпилируется!
fn app() -> Element {
    let mut users = use_signal(|| HashMap::<UserId, UserData>::new());

    rsx! {
        // время жизни здесь не `'static`, не передастся в компонент ListItem
        for (id, user) in users.read().iter() {
            ListItem { key: "{id}", user }
        }
    }
}

// `UserData` не может быть заимствован здесь
#[component]
fn ListItem(user: ReadSignal<UserData>) -> Element {
    rsx! {
        li { "{user.read().name}" }
    }
}
```

В таких сценариях у нас есть несколько вариантов:

- Глубоко клонировать объект `UserData`, отсоединив его время жизни от цикла `for`
- Клонировать отдельные поля объекта `UserData`
- Использовать Хранилища и передать Линзу

Первые два варианта требуют от нас выполнения потенциально дорогостоящих клонирований при рендеринге компонента. Вместо этого мы можем использовать хранилища и линзы, чтобы найти решение с нулевой стоимостью, просто преобразовав наш `use_signal` в вызов `use_store`:

```rust
fn app() -> Element {
    // переключаемся на использование `use_store`
    let mut users = use_store(|| HashMap::<UserId, UserData>::new());

    rsx! {
        for (id, user) in users.iter() {
            ListItem { key: "{id}", user }
        }
    }
}

// И теперь мы можем принять `ReadSignal<UserData>` как проп
#[component]
fn ListItem(user: ReadSignal<UserData>) -> Element {
    rsx! {
        li { "{user.read().name}" }
    }
}
```

Тип `Store<HashMap<K, V>>` — это специальный тип, который реализует реактивность на уровне отдельной записи. Когда мы вставляем или удаляем значения из хранилища `users`, ставится в очередь только *один* повторный рендер. Если мы редактируем отдельную запись в HashMap, перерендерится только один компонент `ListItem`.

Альтернативно, мы могли бы вывести `Store` для нашего типа `UserData` и принять `ReadStore<UserData>`, позволяя нам дальше создавать линзы для конкретных полей нашей записи UserData:

```rust
#[derive(Store)]
struct UserData {
    name: String,
    email: String,
}

fn app() -> Element {
    let users = use_store(|| HashMap::<UserId, UserData>::new());

    rsx! {
        for (id, user) in users.iter() {
            ListItem { key: "{id}", user }
        }
    }
}

#[component]
fn ListItem(user: ReadStore<UserData>) -> Element {
    rsx! {
        li { "{user.name()}" }
    }
}
```

## Расширение Хранилищ Методами

Вы можете расширять типы ваших хранилищ методами с помощью атрибута-макроса `#[store]`. Методы внутри макроса преобразуются в расширяющий трейт, который автоматически реализуется для `Store<T, Lens>`. Макрос автоматически добавляет ограничения на дженерик `Lens` для каждого метода в зависимости от параметра self каждого метода:

- Если метод принимает `&self`, для `Lens` будет добавлено ограничение `Readable` только для этого метода
- Если метод принимает `&mut self`, для `Lens` будет добавлено ограничение `Writable` только для этого метода
- Если метод принимает `self` по значению, не добавляются никакие ограничения

Это означает, что каждый метод может иметь разные ограничения на тип `Lens`, позволяя вам смешивать методы только для чтения и с возможностью записи в одном блоке impl.

```rust
type MappedUserDataStore<Lens> = Store<String, MappedMutSignal<String, Lens, fn(&UserData) -> &String, fn(&mut UserData) -> &mut String>>;

#[store]
impl<Lens> Store<UserData, Lens> {
    // Этот метод требует `Readable` на линзе, так как принимает `&self`
    fn user_email(&self) -> String {
        self.email().cloned()
    }

    // Этот метод требует `Writable` на линзе, так как принимает `&mut self`
    fn clear_name(&mut self) {
        self.name().take();
    }

    // Этот метод не требует никаких ограничений на линзе, так как принимает `self` по значению
    fn into_parts(self) -> (MappedUserDataStore<Lens>, MappedUserDataStore<Lens>) where Self: Copy {
        (self.email(), self.name())
    }
}
```

## Наиболее Эффективное Использование Хранилищ

Надеемся, приведенные здесь примеры показывают, когда хранилища могут быть полезны в ваших приложениях. Может быть заманчиво использовать хранилища *везде*, но во многих случаях сигналов и структур достаточно. Большинство приложений не столкнутся с проблемами производительности, где точный контроль над реактивностью полей структуры дает огромную разницу.

Хранилища наиболее полезны при взаимодействии с внешними типами данных и оптимизации огромных коллекций — не то, что нужно делать каждый день!
