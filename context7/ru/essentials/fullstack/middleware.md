# Промежуточное ПО

Промежуточное ПО (middleware) позволяет вам запускать код до завершения обработки запроса. Затем, на основе входящего запроса, вы можете модифицировать ответ, переписывая, перенаправляя, изменяя заголовки запроса или ответа, или отвечая напрямую.

Dioxus Fullstack предоставляет два основных способа добавления промежуточного ПО в ваше приложение:

- Императивно, используя API Axum на вашем роутере в `dioxus::serve`
- Декларативно, аннотируя отдельные эндпоинты атрибутом `#[middleware]`

## Что такое промежуточное ПО?

В веб-приложениях промежуточное ПО — это функции, которые вызываются до и после обработки запроса вашей логикой эндпоинта.

Базовый веб-фреймворк, на котором построен Dioxus Fullstack, — Axum — не определяет собственную специализированную систему промежуточного ПО. Вместо этого он опирается на более широкую экосистему, интегрируясь с более фундаментальными крейтами [`tower`](https://github.com/tower-rs/tower) и [`hyper`](https://github.com/hyperium/hyper).

Axum *действительно* предоставляет простой способ написания промежуточного ПО с помощью `middleware::from_fn`:

```rust
axum::middleware::from_fn(
    |request: Request, next: Next| async move {
        // Читаем и записываем содержимое входящего запроса
        println!("Headers: {:?}", request.headers());

        // И затем запускаем запрос, модифицируя и возвращая ответ
        next.run(request).await
    },
)
```

Промежуточное ПО даёт вам как *право чтения*, так и *право записи* как для *запроса*, так и для *ответа* обработчика. Это чрезвычайно мощно!

С помощью промежуточного ПО вы можете реализовать широкий спектр функциональности:

- Логирование и телеметрия
- Ограничение частоты запросов (rate limiting)
- Валидация
- Сжатие
- CORS, CSRF
- Аутентификация и авторизация
- Кэширование

В более широкой экосистеме Rust существует множество различных сторонних крейтов для промежуточного ПО.

Два основных крейта для поиска промежуточного ПО:

- [Tower](https://docs.rs/tower/latest/tower/): Базовая библиотека для сетевого взаимодействия
- [Tower-HTTP](https://github.com/tower-rs/tower-http): Специализированная библиотека HTTP-промежуточного ПО

## Промежуточное ПО на роутере

Поскольку Dioxus построен на Axum, вы можете использовать многие API Axum напрямую. Dioxus Fullstack не предоставляет никаких специализированных обёрток вокруг промежуточного ПО Axum — вы можете просто прикрепить их к вашему роутеру в `dioxus::serve`:

```rust
dioxus::serve(|| async move {
    use axum::{extract::Request, middleware::Next};
    use dioxus::server::axum;

    Ok(dioxus::server::router(app)
        // мы можем применить слой ко всему роутеру, используя метод `.layer` axum
        .layer(axum::middleware::from_fn(
            |request: Request, next: Next| async move {
                // Читаем входящий запрос
                println!("Request: {} {}", request.method(), request.uri().path());

                // Запускаем обработчик, возвращая ответ
                let res = next.run(request).await;

                // Читаем/записываем ответ
                println!("Response: {}", res.status());

                res
            },
        )))
});
```

Крейт Tower-HTTP предоставляет ряд полезных слоёв промежуточного ПО для добавления в ваше приложение. Объект `ServiceBuilder` может использоваться для эффективной сборки `Service`, который обрабатывает широкий спектр действий промежуточного ПО:

```rust
// Используем API `ServiceBuilder` из tower для построения стека tower middleware,
// оборачивающего наш обработчик запросов.
let middleware = ServiceBuilder::new()
    // Помечаем заголовок запроса `Authorization` как чувствительный, чтобы он не показывался в логах
    .layer(SetSensitiveRequestHeadersLayer::new(once(AUTHORIZATION)))
    // Высокоуровневое логирование запросов и ответов
    .layer(TraceLayer::new_for_http())
    // Делимся `Arc<State>` со всеми запросами
    .layer(AddExtensionLayer::new(Arc::new(state)))
    // Сжимаем ответы
    .layer(CompressionLayer::new())
    // Распространяем `X-Request-Id` из запросов в ответы
    .layer(PropagateHeaderLayer::new(HeaderName::from_static("x-request-id")))
    // Если у ответа известен размер, устанавливаем заголовок `Content-Length`
    .layer(SetResponseHeaderLayer::overriding(CONTENT_TYPE, content_length_from_response))
    // Авторизуем запросы, используя токен
    .layer(ValidateRequestHeaderLayer::bearer("passwordlol"))
    // Принимаем только application/json, application/* и */* в заголовке ACCEPT запроса
    .layer(ValidateRequestHeaderLayer::accept("application/json"))
    // Обертываем `Service` в наш стек промежуточного ПО
    .service_fn(handler);
```

Затем вы можете прикрепить этот сервис как слой к вашему роутеру:

```rust
dioxus::serve(|| async move {
    use axum::{extract::Request, middleware::Next};
    use dioxus::server::axum;

    // Собираем объект промежуточного ПО из ServiceBuilder
    let middleware = ServiceBuilder::new()
        .layer(/* */)
        .layer(/* */)
        .layer(/* */);

    Ok(dioxus::server::router(app).layer(middleware))
});
```

Axum рекомендует инициализировать несколько промежуточных слоёв на объекте `ServiceBuilder` для максимальной производительности, но вы также можете прикреплять слои напрямую к роутеру:

```rust
dioxus::serve(|| async move {
    use axum::{extract::Request, middleware::Next};
    use dioxus::server::axum;

    Ok(
        dioxus::server::router(app)
            .layer(/* */)
            .layer(/* */)
            .layer(/* */)
    )
});
```

## Промежуточное ПО на отдельных маршрутах

Если вам нужно применить промежуточное ПО только к нескольким конкретным маршрутам, вы можете использовать атрибут `#[middleware]`. В отличие от промежуточного ПО уровня роутера, промежуточное ПО уровня маршрута будет применено только к конкретному эндпоинту. Как альтернатива, вы можете регистрировать маршруты один за другим на axum-роутере с выделенными вызовами `.layer()`.

Например, мы можем захотеть добавить промежуточное ПО «таймаут» к конкретной серверной функции. Это промежуточное ПО остановит выполнение серверной функции, если оно достигнет определённого таймаута:

```rust
#[cfg(feature = "server")]
use {std::time::Duration, tower_http::timeout::TimeoutLayer};

// Add a timeout middleware to the server function that will return an error if the function takes longer than 1 second to execute
#[post("/api/timeout")]
#[middleware(TimeoutLayer::new(Duration::from_secs(1)))]
pub async fn timeout() -> Result<(), ServerFnError> {
    tokio::time::sleep(Duration::from_secs(2)).await;
    Ok(())
}
```

Под капотом Dioxus Fullstack создаёт объект `MethodRouter`, а затем автоматически прикрепляет эти слои с помощью вызовов `.layer()`.

## Кэширование и промежуточное ПО

В главе о серверном рендеринге мы подробно обсуждали, как Dioxus Fullstack спроектирован вокруг клиентского рендеринга, а SSR является дополнительным улучшением. Одно из улучшений — возможность добавить заголовок `Cache-Control` к HTML-ответам, позволяя нашему CDN и обратному прокси снизить нагрузку на наш сервер. Когда присутствует заголовок `Cache-Control`, прокси может кэшировать ответы.

> Очень важно отметить, что промежуточное ПО может «сломать» кэш — даже случайно!

Если вы используете промежуточное ПО для управления сессиями или аутентификации, можно легко случайно закэшировать страницы, которые не должны кэшироваться. Например, новостной сайт может захотеть кэшировать свою домашнюю страницу:

```rust
dioxus::server::router(app)
    .layer(axum::middleware::from_fn(
        |request: Request, next: Next| async move {
            // Если маршрут — `/home`, кэшируем страницу
            let is_home = request.uri() == "/home";

            let res = next.run(request).await;

            if is_home {
                res.headers_mut().insert("Cache-Control", "max-age=10800")
            }

            res
        }
    ))
```

В конечном итоге мы можем добавить функцию, позволяющую пользователям настраивать свою домашнюю страницу. Мы можем добавить слой сессий к нашему роутеру:

```rust
dioxus::server::router(app)
    .layer(session_layer) // новый слой сессий
    .layer(caching_layer)
```

Если мы не будем осторожны, мы можем случайно закэшировать *домашнюю страницу вошедшего пользователя*! Кэширование обычно основано на URL запроса, но промежуточное ПО также работает с заголовками. Если мы показываем динамический контент на основе заголовков (например, auth или сессии), нам нужно позаботиться о том, чтобы кэшировать только определённые ответы.

Многие обратные прокси имеют возможность настраивать кэширование на основе заголовков запроса. Мы предлагаем изучить настройку обратного прокси вашей платформы развёртывания или реализовать более умное промежуточное ПО кэширования самостоятельно.
