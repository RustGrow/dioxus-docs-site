# Настройка проекта

Приложения Dioxus Fullstack имеют несколько иную структуру, чем клиентские приложения. Это отличие влияет на то, как мы организуем наши приложения, требуя большей внимательности при добавлении зависимостей и включении кода.

В этой главе мы рассмотрим, как использовать флаги функций (feature flags) и цели cargo для структурирования наших приложений под fullstack-разработку.

> Dioxus предоставляет несколько шаблонов с помощью `dx new` для автоматической инициализации новых fullstack-проектов.
>
> Если вы хотите быстро начать работу, мы рекомендуем использовать один из встроенных шаблонов, а затем перейти к следующей главе.

## Разделение сервера и клиента

«Fullstack»-приложение фактически состоит как минимум из двух отдельных бинарников:

- Клиентский бинарник, который запускает веб-, десктоп- или мобильное приложение
- Серверный бинарник, который рендерит начальный HTML и запускает серверные функции

Поскольку наше клиентское приложение и серверное приложение ориентированы на разные платформы, нам нужно включать разный код и разные зависимости. Вы можете представлять «сервер» как ещё одну платформу для вашего приложения, точно так же, как вы можете ориентироваться одновременно на iOS и Android. У сервера будут другие зависимости, чем у клиентского приложения, поэтому вам необходимо правильно настроить `Cargo.toml` вашего приложения и флаги сборки.

## Как DX собирает ваше приложение

Наш инструмент сборки DX способен одновременно собирать и клиент, и сервер вашего приложения. Если включён флаг `--hotpatch`, DX также будет автоматически горячо перезагружать и клиентский, и серверный код.

При разработке приложения вы обычно будете использовать `dx serve`. Эта команда принимает стандартные аргументы, которые вы могли бы передать в `cargo run`:

```sh
# Мы можем настроить фичи, профиль или режим релиза сборки
dx serve --features "spicy" --release

# Мы можем указать примеры, пакеты и бинарники
dx serve --example dogs
```

Под капотом DX автоматически определяет, есть ли у целевого приложения серверная вариация, проверяя его `Cargo.toml` на наличие фичи Cargo под названием «server». В этой фиче Cargo вы должны включить фичу `server` у Dioxus:

```toml
[features]
server = ["dioxus/server"]
```

DX также будет искать конкретные клиентские фичи (`"web"` / `"desktop"` / `"mobile"`) и включать соответствующую фичу в зависимости от целевой платформы. DX использует концепцию «платформы» для различения типов сборок друг от друга.

Чтобы задать платформу сборки, вы можете использовать `--web`, `--desktop`, `--ios` и т. д. Когда вы указываете платформу, DX также включает соответствующую фичу в вашем Cargo.toml:

```toml
# включается с `--web`
web = ["dioxus/web"]

# включается с `--desktop`
desktop = ["dioxus/desktop"]

# включается с `--mobile`
mobile = ["dioxus/mobile"]
```

Запуск команды может выглядеть так:

```sh
# устанавливает target=wasm32-unknown-unknown, features="web", profile="wasm-dev"
dx serve --web

# устанавливает target=host, features="desktop", profile="desktop-dev"
dx serve --desktop

# устанавливает target=aarch64-apple-ios-sim, features="mobile", profile="ios-dev"
dx serve --ios
```

Если ваша зависимость `dioxus` включает фичу `fullstack`, DX распознаёт это приложение как fullstack-приложение и затем создаёт две сборки, каждую с отдельной платформой:

```toml
[dependencies]
dioxus = { version = "0.7", features = ["fullstack"] }

[features]
web = ["dioxus/web"]
server = ["dioxus/server"]
```

Внутри DX разбивает вашу входную команду на две отдельные команды `cargo build`, каждая с разной платформой.

![Разделение сервера и клиента](/assets/06_docs/server_split.png)

Флаги функций для клиента и сервера автоматически генерируются CLI при запуске `dx new` с включённым fullstack. Если вы создаёте проект с нуля, вам нужно будет добавить флаги функций вручную.

> Если вы не знакомы с фичами в Rust, вы можете прочитать больше о флагах функций в [справочнике cargo](https://doc.rust-lang.org/cargo/reference/features.html).

## Настройка сборок

Fullstack-приложение состоит из двух отдельных бинарников, поэтому DX предоставляет способ настроить каждый из них. Обычно стандартной команды `dx serve` достаточно, но для сложных настроек приложения, требующих кастомизации под каждую цель, вы можете использовать модификаторы `@client` и `@server` для передачи целевых аргументов cargo каждой из сторон:

```sh
dx serve \
  @client --ios --features "optimizations" \
  @server --bin server
```

Этот синтаксис позволяет иметь две отдельные точки входа для нашего приложения. Это может быть чрезвычайно полезно, если у вас уже есть бэкенд, и вы хотите запустить его вместе с вашим Dioxus-фронтендом.

По умолчанию DX изолирует ваши серверные и клиентские сборки, используя Cargo Profiles. Профили Cargo позволяют нам задавать определённые модификаторы сборки, такие как opt-level, отладочные символы, LTO и другие оптимизации.

DX будет использовать эти профили:
- `web-dev` / `web-release`: ориентация на веб с `--web`
- `server-dev` / `server-release`: ориентация на сервер (неявно, или с `--server`)
- `desktop-dev` / `desktop-release`: ориентация на десктоп-приложения с `--desktop`
- `ios-dev` / `ios-release`: ориентация на iOS-приложения с `--ios`
- `android-dev` / `android-release`: ориентация на Android-приложения с `--android`

Эти профили соответствуют 1:1 «платформам», которые поддерживает DX. Обратите внимание, что `платформа` — это просто способ для DX изолировать две сборки друг от друга. Вы можете полностью настроить сборку, включая:

- `--renderer`: переключение между различными рендерами от первого лица (например, `--renderer native`)
- `--bundle`: формат бандла сборки (`.app`, `.apk`, `.ipa` и т. д.)
- все опции cargo (`--features`, `--target`, `--profile`, `--bin` и т. д.)

## Добавление зависимостей только для сервера

Многие зависимости, такие как [`tokio`](https://docs.rs/tokio/latest/tokio/index.html), не могут быть скомпилированы в WebAssembly, и поэтому должны собираться только для сервера. Если эти зависимости включены при сборке WASM-бандла, вы получите загадочные ошибки компиляции. Поэтому нам нужно быть внимательными и не добавлять случайно серверные зависимости в наше клиентское приложение.

Например, если мы хотим взаимодействовать с файловой системой в серверной функции, мы можем захотеть добавить `tokio`. Крейт `tokio` предоставляет утилиты для работы с асинхронным вводом-выводом с абстракциями вроде [`tokio::fs::File`](https://docs.rs/tokio/latest/tokio/fs/struct.File.html). К сожалению, если мы попытаемся добавить `tokio` с полным набором фич (`full`), мы получим ошибку компиляции:

```toml
[dependencies]
# ...
# ❌ Если tokio добавлен как обязательная зависимость, он будет включён и в сервер,
# и в веб-бандл. Веб-бандл не соберётся, потому что tokio не совместим с wasm
tokio = { version = "1", features = ["full"] }
```

```sh
error[E0432]: unresolved import `crate::sys::IoSourceState`
  --> /Users/user/.cargo/registry/src/index.crates.io-6f17d22bba15001f/mio-1.0.2/src   |source.rs:14:5
14 | use crate::sys::IoSourceState;
   |     ^^^^^^^^^^^^^^^^^^^^^^^^^ no `IoSourceState` in `sys`
...
```

Поскольку мы добавили `tokio` как зависимость и для сервера, и для клиентского бинарника, cargo пытается скомпилировать его для каждой цели. Это завершается неудачей, потому что `tokio` не совместим с целью `wasm32-unknown-unknown`.

Чтобы исправить проблему, мы можем **сделать зависимость опциональной и включать её только в серверной фиче**:

```toml
[dependencies]
# ...
# ✅ Поскольку зависимость tokio опциональна, она не включается в клиентский бандл.
tokio = { version = "1", features = ["full"], optional = true }

[features]
# ...
# ✅ Поскольку зависимость tokio включена в серверную фичу, она включается в
# серверный бинарник.
server = ["dioxus/server", "dep:tokio"]
```

Теперь при сборке с `dx serve` проект компилируется успешно!

## Добавление зависимостей только для клиента

Многие зависимости, такие как [`wasm-bindgen`](https://docs.rs/wasm-bindgen/latest/wasm_bindgen/index.html) и [`web-sys`](https://docs.rs/web-sys/latest/web_sys/index.html), совместимы только с клиентом. В отличие от серверных зависимостей, эти зависимости могут компилироваться под нативные цели, но они вызовут панику при использовании вне браузера.

Вы можете сократить время сборки для вашего сервера и нативных бинарников, включая веб-зависимости только в браузерный клиентский бинарник.

Вместо добавления веб-зависимостей к каждому бинарнику в вашем проекте, как здесь:
```toml
[dependencies]
# ...
# ❌ Если web-sys добавлен как обязательная зависимость, он будет включён в сервер,
# нативный и веб-бандл, что увеличит время сборки.
web-sys = { version = "0.3.60", features = ["console"] }
```

Вы можете сделать зависимость опциональной и включить её только в фиче `web` в вашем `Cargo.toml`:
```toml
[dependencies]
# ...
# ✅ Поскольку зависимость web-sys опциональна, она не включается в серверные и
# нативные бандлы.
web-sys = { version = "0.3.60", features = ["console"], optional = true }

[features]
# ...
# ✅ Поскольку зависимость web-sys включена в фичу web, она включается в веб-бандл.
web = ["dioxus/web", "dep:web-sys"]
```

## Управление импортами, специфичными для бинарников

Когда вы настроили зависимости, специфичные для конкретного бинарника, вам нужно скорректировать импорты, чтобы импортировать зависимости только при сборке для того бинарника, который их включает.

Например, если `tokio` включён только в серверной фиче, вам нужно импортировать его так:
```rust
Since the tokio dependency is only enabled in the server feature,
// we need to only import it when the server feature is enabled.
#[cfg(feature = "server")]
use {tokio::fs::File, tokio::io::AsyncReadExt};
```

Вам также нужно компилировать любое использование зависимости только когда соответствующая фича включена:
```rust
Since the tokio dependency is only enabled in the server feature,
// we need to only compile any usage of the dependency when the server feature is enabled.
#[cfg(feature = "server")]
async fn read_file() -> Result<String, std::io::Error> {
    let mut file = File::open("path/to/file").await?;
    let mut contents = String::new();
    file.read_to_string(&mut contents).await?;
    Ok(contents)
}

// The bodies of server functions automatically only compile when the server feature is enabled.
#[server]
async fn get_file_contents() -> Result<String> {
    let mut file = File::open("path/to/file").await?;
    let mut contents = String::new();
    file.read_to_string(&mut contents).await?;
    Ok(contents)
}
```

Бывает удобнее сгруппировать серверный или клиентский код в модуль, который компилируется только при включённой фиче:
```rust
// Instead of configuring each item that is only used in the server, you can group
// them into a module that is only compiled when the server feature is enabled.
    #[cfg(feature = "server")]
    mod tokio_utilities {
        use std::path::PathBuf;
        use tokio::fs::File;
        use tokio::io::AsyncReadExt;

        pub async fn read_file(path: PathBuf) -> Result<String, std::io::Error> {
            let mut file = File::open(path).await?;
            let mut contents = String::new();
            file.read_to_string(&mut contents).await?;
            Ok(contents)
        }
    }

// Then you can define your server functions using shared utilities you defined for
// server only code.
    #[server]
    async fn get_file_contents() -> Result<String> {
        let file = tokio_utilities::read_file(PathBuf::from("path/to/file")).await?;
        Ok(file)
    }

    #[server]
    async fn get_other_file_contents() -> Result<String> {
        let file = tokio_utilities::read_file(PathBuf::from("path/to/other/file")).await?;
        Ok(file)
    }
```

> В [справочнике по Rust](https://doc.rust-lang.org/reference/conditional-compilation.html) есть больше информации об условной компиляции в Rust.

## Отдельные крейты для фронтенда и бэкенда

Если вы хотите, вы можете разделить ваш фронтенд и бэкенд на отдельные крейты. Это может быть полезно для более крупных проектов, где у вас есть отдельные сложные точки входа для веба, десктопа и мобильных устройств.

Настройки воркспейса (workspace) добавляют дополнительную сложность, но они могут значительно упростить совместное использование типов данных и функций между несколькими разными проектами. Например, у вас может быть один крейт с API, используемый несколькими разными приложениями.

В таких случаях мы можем организовать наш воркспейс следующим образом:

```
├── Cargo.toml
└── packages/
    ├── cat-app/
    │     ...
    ├── dog-app/
    │     ...
    └── pet-api/
          ...
```

Если вы используете Dioxus Fullstack, вы можете импортировать серверные функции вашего `pet-api` для вызова из вашего UI. В клиентском приложении вы можете затем импортировать крейт `pet-api`:

```toml
[dependencies]
pet-api = { workspace = true }
```

Для запуска сервера вы можете выбрать один из двух вариантов:

1. Запустить сервер `pet-api` из клиентского проекта
2. Запустить основной бинарник крейта `pet-api`

Если ваш сервер достаточно прост, то вариант 1 может быть неплохим, поскольку он автоматически интегрируется с `dx serve`.

Однако если вы выбираете выделенный серверный бинарник, то вам нужно будет использовать модификаторы `@client` и `@server` для использования разных бинарников:

```sh
dx serve @client --bin dog-app @server --bin pet-api
```

Встроенный шаблон Dioxus «Workspace» может послужить хорошей отправной точкой для настройки воркспейса.
