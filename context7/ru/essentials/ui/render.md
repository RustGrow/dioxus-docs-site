# Согласование: как компоненты рендерятся

Мы подробно рассмотрели, как определяются компоненты и их свойства, но ещё не рассмотрели, как они фактически работают. Компоненты Dioxus — это *не* обычные Rust-функции. Хотя технически возможно вызывать их как обычные Rust-функции, компоненты полагаются на *активный* runtime Dioxus для правильной работы.

Чтобы правильно использовать компоненты, важно понимать основы того, как поток состояния, как создаются элементы и как хранится состояние. Мы кратко опишем, как работает состояние, но состояние может быть сложным, поэтому мы посвятили ему отдельную [главу](../basics/index.md).

## Компоненты рендерятся

В Dioxus термин "рендеринг" относится к процессу, который Dioxus использует для вызова ваших функций компонентов и отрисовки элементов на экране. Когда вы вызываете `dioxus::launch`, Dioxus настраивает runtime приложения и затем вызывает предоставленный начальный компонент для создания начального `Element`. Этот элемент объявляет стили, макеты, дочерние элементы и обработчики событий. Dioxus преобразует ваши элементы в вызовы отрисовки и преобразует ваши обработчики событий в нативные обработчики событий.

![Component Loop](/assets/07/render-calls.png)

Поскольку Dioxus использует "виртуальное" дерево, элементы в вашем RSX-дереве не являются фактическими ссылками на "реальные" узлы в рендерере. Например, тип Dioxus `Element` — это не полный объект [HTMLElement](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement). Когда Dioxus получает ваш начальный Element, он преобразует ваши виртуальные элементы в реальные элементы и вызовы отрисовки с помощью платформо-зависимого рендерера.

## Компоненты перерендериваются

Компоненты будут перезапускаться при изменении состояния, от которого они зависят. После того как начальный Element был отрисован платформо-зависимым рендерером, Dioxus слушает события на ваших элементах. Когда событие получено, вызываются соответствующие обработчики событий, и ваш код имеет возможность изменить состояние. Мутация состояния — это основной механизм, с помощью которого Dioxus узнаёт, что нужно снова запустить функции вашего компонента и искать изменения в дереве.

![Component Loop](/assets/07/render-loop.png)

Dioxus считает состояние изменённым в двух ситуациях:

- Свойства компонента изменились, как определено его реализацией `PartialEq`
- Внутреннее [состояние](../basics/index.md), от которого зависит компонент, изменилось (например, `signal.write()`) и запланировано "обновление"

```rust
// When the name property changes, the component will rerender
#[component]
fn Button(name: String) -> Element {
    let mut count = use_signal(|| 0);
    log!("Component rerendered with name: {name} count: {count}");

    rsx! {
        h3 { "Hello, {name}!" }
// MyComponent reads the `count` signal, so it will rerender
// whenever `count` changes.
        "Count: {count}"
        button {
// When the button is clicked, it increments the count signal
            onclick: move |_| count += 1,
            "Increment"
        }
    }
}
```

После того как компонент запускается снова, Dioxus сравнит старый `Element` и новый `Element` в поисках изменений. Runtime Dioxus определит минимальное количество вызовов отрисовки, необходимых для изменения старого интерфейса в соответствии с желаемым. Этот процесс сравнения называется "diffing" (диффинг). Dioxus оптимизирует диффинг, сравнивая только динамические части RSX, поэтому статические элементы не проверяются на изменения (подробнее см. в этом [блог-посте](https://dioxuslabs.com/blog/templates-diffing)). Весь этот цикл — Рендеринг, Отображение, Прослушивание, Мутация — называется "согласование" (reconciliation), и Dioxus имеет одну из самых производительных реализаций среди всех UI-фреймворков.

## Компоненты — функции состояния

Компоненты — это чистая функция вашего текущего состояния приложения в форме `fn(State) -> Element`. Они читают состояние из различных источников, таких как props, [хуки](../basics/hooks.md) или [контекст](../basics/context.md), и возвращают представление текущего интерфейса как `Element`.

Мы уже видели, как компоненты отображают состояние props в интерфейс, но состояние может также поступать из самого компонента в виде хуков. Например, мы можем использовать сигнал для отслеживания счётчика в нашем компоненте. Компонент определяет отображение от текущего состояния сигнала к интерфейсу, который должен быть отрендерен:

```rust
#[component]
pub fn MyStatefulComponent() -> Element {
    let mut count = use_signal(|| 0);

    rsx! {
        div {
            h3 { "Count: {count}" }
            button { onclick: move |_| count += 1, "Increment" }
        }
    }
}
```

При создании приложений Dioxus важно понимать, что ваш UI-код — это декларация того, каким вы хотите видеть свой интерфейс, — он не содержит никакой логики о том, как обновить интерфейс, чтобы достичь этого. Dioxus сам отвечает за приведение интерфейса в соответствие с вашим желаемым вводом.

## Компоненты — чистые функции

Тело компонента должно быть чистым. Чистые функции всегда возвращают один и тот же вывод для одного и того же ввода и не имеют побочных эффектов. Например, эта функция double чистая:

```rust
fn double(x: i32) -> i32 {
    // x * 2
}
```

Если вы вызовете `double(2)`, она всегда вернёт `4`.

Однако эта функция не чистая, потому что она изменяет внешнее состояние:

```rust
static GLOBAL_COUNT: AtomicI32 = AtomicI32::new(0);

fn increment_global_count() -> i32 {
    GLOBAL_COUNT.fetch_add(1, Ordering::SeqCst)
}
```

Когда вы вызываете `increment_global_count()` в первый раз, она вернёт `0`, но в следующий раз вернёт `1`. Эта функция имеет побочные эффекты, потому что изменяет глобальное состояние.

Помимо глобальных переменных, контекст и хуки также являются внешним состоянием в компонентах. Компоненты не должны изменять состояние из контекста или хуков во время рендеринга:

```rust
#[component]
fn MyImpureComponent() -> Element {
    let mut count = use_signal(|| 0);

❌ Modifying the count signal from a hook is a side effect.
Dioxus may try to rerender the component with the new value,
// which can lead to unexpected behavior or infinite loops.
    count += 1;

    rsx! {
        div {
            h3 { "Count: {count}" }
        }
    }
}
```

Побочные эффекты, изменяющие состояние, должны размещаться в обработчиках событий или [эффектах](../advanced/breaking-out.md#synchronizing-dom-updates-with-use_effect), которые запускаются после того, как компонент отрендерился. Это гарантирует, что выход компонента стабилен и предсказуем.

```rust
#[component]
fn MyPureComponent() -> Element {
    let mut count = use_signal(|| 0);

    rsx! {
        div {
            h3 { "Count: {count}" }
            button {
✅ Event handlers can modify state and have side effects.
                onclick: move |_| count += 1,
                "Increment"
            }
        }
    }
}
```

Если вы обнаружите, что пишете компоненты, которые *не* чистые, то, скорее всего, вы неправильно используете или не понимаете реактивный парадигм. Мутации должны размещаться либо в обработчиках событий как ответ на действия пользователя, либо в долгоживущих асинхронных задачах как ответ на фоновую обработку.

## Сходство с React

Если вы знакомы с библиотеками вроде ReactJS, то эта парадигма вам знакома. Dioxus заимствует многие идеи из React, и ваши существующие знания будут чрезвычайно полезны. Если что-то здесь вызывает затруднение, загляните в [документацию React](https://react.dev/learn) или проведите дополнительное исследование по реактивной системе React.
