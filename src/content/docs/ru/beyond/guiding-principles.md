# Общие цели

Этот документ описывает некоторые общие цели проекта Dioxus. Эти цели не являются неизменными, но они представляют собой общие ориентиры для проекта.

Цель Dioxus — сделать простым создание **кроссплатформенных приложений, которые масштабируются**.

## Кроссплатформенность

Dioxus спроектирован так, чтобы быть кроссплатформенным по умолчанию. Это означает, что должно быть легко создавать приложения, работающие в вебе, на десктопе и на мобильных устройствах. Однако Dioxus также должен быть достаточно гибким, чтобы позволять пользователям включать платформенно-специфичные фичи, когда это необходимо. `use_eval` — один из примеров этого. По умолчанию Dioxus не предполагает, что платформа поддерживает JavaScript, но предоставляет хук, позволяющий включить JavaScript при необходимости.

## Производительность

По мере роста приложений Dioxus они должны оставаться относительно производительными без необходимости ручных оптимизаций. Будут случаи, когда ручные оптимизации нужны, но Dioxus должен стремиться сделать такие случаи как можно более редкими.

Одно из преимуществ архитектуры ядра Dioxus — это разумная производительность даже при частых перерисовках компонентов. Она основана на Virtual DOM, который выполняет диффинг, что должно предотвращать ненужные перерисовки даже при частом перезапуске больших частей дерева компонентов. Помимо этого, Dioxus группирует статические части дерева RSX вместе, чтобы полностью пропускать их диффинг.

## Безопасность типов

По мере роста команд огромное преимущество даёт безопасность типов Rust. Dioxus должен использовать это преимущество, чтобы облегчить создание приложений в больших командах.

Чтобы в полной мере использовать систему типов Rust, Dioxus должен избегать публичных типов `Any` и API, основанных на строках, где это возможно.

## Опыт разработчика

Dioxus должен быть лёгким в изучении и эргономичным в использовании.

- API Dioxus стремится оставаться близким к API React, где это возможно. Это облегчает изучение Dioxus тем, кто уже знает React.

- Мы можем избежать компромисса между простотой и гибкостью, предоставляя несколько уровней API: один для очень распространённых случаев использования, другой для низкоуровневого контроля.

  - Хуки: крейт hooks содержит наиболее распространённые случаи использования, но `use_hook` предоставляет способ доступа к базовому persistent value, если это необходимо.
  - Паттерн builder в платформенных Config: паттерн builder используется для задания наиболее распространённого случая использования по умолчанию, но пользователи могут изменить значения по умолчанию, если это необходимо.

- Документация:
  - Все публичные API должны иметь Rust-документацию.
  - Примеры должны предоставляться для всех публичных фич. Эти примеры служат как документация, так и тестирование. Они проверяются CI, чтобы гарантировать, что они продолжают компилироваться.
  - Наиболее распространённые рабочие процессы должны быть задокументированы в руководстве.
