# Обработка ошибок в Fullstack

Ошибки, к сожалению, неизбежны в разработке ПО. Даже в Rust приложения могут вести себя не так, как ожидается, а пользовательские запросы могут быть некорректными.

В таких случаях вы можете захотеть показать пользователю страницу ошибки, одновременно возвращая соответствующий код состояния.

## Создание ошибки

Вспомните из главы [Серверные функции](./server-functions.md), что все серверные функции должны возвращать `Result<T>`:

```rust
#[post("/api/user/login")]
pub async fn login() -> Result<()> {
    ...
}
```

Поскольку серверные функции вызываются с клиента, им нужен какой-то способ выразить *и* сбой запроса, *и* сбой сервера. Если пользователь офлайн, мы хотим надёжно вернуть ошибку офлайн и статус в UI.

Также вспомните, что серверные функции могут возвращать несколько разных типов ошибок:

- `ServerFnError`: широкий тип ошибки, охватывающий сбои запросов и сбои сервера
- `anyhow::Error`: универсальный тип ошибки, который приводит своё внутреннее значение
- `CapturedError`: дёшево клонируемая обёртка над `anyhow::Error`
- `StatusCode`: конкретный HTTP-код состояния
- `HttpError`: конкретный HTTP-код состояния и сообщение
- Пользовательские ошибки: пользовательские ошибки, реализующие `Serialize + Deserialize + AsStatusCode`

Dioxus будет пытаться привести ошибки серверных функций и захваченные ошибки к кодам состояния таким образом, чтобы возвращённая страница получала соответствующий HTTP-статус.

Если ошибка не приводится к известному типу ошибки, похожему на код состояния, то запрос по умолчанию вернёт `500 INTERNAL SERVER ERROR`.

```rust
#[post("/api/user/login")]
pub async fn login() -> Result<()> {
    // Это вернёт код состояния 500
    return Err(anyhow::anyhow!("Bad request!").into());

    ...
}
```

Тип ошибки `OrHttpError` делает эмиссию кодов состояния довольно простой с помощью своих методов-расширений для `Result<T>`, `Option<T>` и `bool`.

```rust
#[post("/api/user/login")]
pub async fn login() -> Result<()> {
	authenticate_user()
        // этот метод приходит из `OrHttpError`
		.or_unauthorized("You must be logged in to view this resource")?;
 ..
}
```

## Коды состояния ошибок всплывают

В случае ошибки Dioxus извлекает код состояния для ответа, приводя ошибки, которые всплывают до корневого компонента.

Например, это пример приложения, не предоставляющего корневую границу ошибок, и поэтому все ошибки будут всплывать до корня:

```rust
fn app() -> Element {
    let post_data = use_loader(move || get_post())?;

    rsx! {
        p { "{post_data}" }
    }
}

// Этот эндпоинт всегда выбрасывает ошибку
#[get("/api/post/")]
async fn get_post() -> Result<String, HttpError> {
    HttpError::not_found("Post not found")
}
```

Если вы выполните `curl` к приложению, вы заметите, что оно возвращает код состояния `404`.

Если мы хотим перехватить ошибку и предоставить красивый fallback UI, мы можем использовать `ErrorBoundary`. Обратите внимание, что когда мы перехватываем ошибку, мы должны явно установить HTTP-код состояния на исходящем ответе с помощью `FullstackContext::commit_error_status`:

```rust
fn app() -> Element {
    rsx! {
        ErrorBoundary {
            handle_error: move |err| {
                // Чтобы гарантировать, что HTTP-статус всё ещё установлен правильно, нам нужно вызвать `commit_error_status`
                let http_error = FullstackContext::commit_error_status(err.error().unwrap());

                // и затем мы можем отрендерить красивый fallback UI
                rsx! { "Произошла ошибка! {http_error:?}" }
            },
            Post {}
        }
    }
}

fn Post() -> Element {
    let post_data = use_loader(move || get_post())?;
    rsx! { p { "{post_data" } }
}
```

Функция `commit_error_status` на `FullstackContext` извлекает HTTP-статус из `CapturedError`, а затем модифицирует исходящий ответ соответствующим образом.


## Макет ошибок с роутером

Если вы используете Dioxus Router для маршрутизации вашего приложения, то может быть не сразу очевидно, как интегрировать пользовательские страницы ошибок в ваше приложение.

В таких случаях мы применяем аналогичный подход с `ErrorBoundary`. Мы можем либо обернуть наш компонент `Router {}` в границу ошибок, либо добавить макет (layout) в наше приложение, который рендерит fallback UI.

```rust
// Определение роутера с макетом `ErrorLayout`
#[derive(Routable, PartialEq, Clone, Debug)]
enum Route {
    #[layout(ErrorLayout)]
    #[route("/")]
    Home,

    #[route("/blog/:id")]
    Blog { id: u32 },
}

// А затем наш Outlet обёрнут в fallback UI
#[component]
fn ErrorLayout() -> Element {
    rsx! {
        ErrorBoundary {
            handle_error: move |err: ErrorContext| {
                let http_error = FullstackContext::commit_error_status(err.error().unwrap());
                match http_error.status {
                    StatusCode::NOT_FOUND => rsx! { div { "404 — Страница не найдена" } },
                    _ => rsx! { div { "Произошла неизвестная ошибка" } },
                }
            },
            Outlet::<Route> {}
        }
    }
}
```

Использование макетов для страниц ошибок чрезвычайно мощно. Вы можете изолировать fallback UI для конкретных частей страницы, одновременно правильно устанавливая возвращаемый код состояния.

Например, UI GitHub сохраняет большую часть своего интерфейса, изолируя сообщение 404 только для просмотрщика исходного кода:

![Github Fallback UI](/assets/07/github-fallbackui.avif)

Это лучший пользовательский опыт — рендерить веб-страницу, которая визуально согласована, одновременно возвращая соответствующий код состояния.
