# Нативные клиенты

До сих пор мы сосредотачивались на использовании fullstack вместе с веб-приложением. Однако не все приложения, которые вы будете создавать с Dioxus, будут загружаться в веб-браузере. Dioxus также поддерживает мобильные и десктопные приложения.

На этих платформах fullstack работает немного иначе. Вы всё ещё можете использовать серверные функции, но такие вещи, как серверный рендеринг, больше не применяются.

## Разработка нативного fullstack-приложения

Разработка нативного fullstack-приложения работает точно так же, как разработка fullstack веб-приложения. Убедитесь, что ваш `Cargo.toml` имеет соответствующие фичи:

```toml
[dependencies]
dioxus = { version = "0.7", features = ["fullstack"] }

[features]
server = ["dioxus/server"]
desktop = ["dioxus/desktop"]
```

А затем, чтобы запустить приложение, используйте `dx serve --<платформа>`:

```sh
dx serve --desktop
```


## Серверные функции для нативного приложения

Когда вы создаёте нативное приложение, которое полагается на серверные функции, вы можете свободно вызывать любую серверную функцию точно так же, как и с веб-приложением.

Это простое приложение «hello world» работает одинаково на вебе, десктопе и мобильных устройствах:

```rust
use dioxus::prelude::*;

fn main() {
    dioxus::launch(|| {
        let mut message = use_action(get_message);

        rsx! {
            h1 { "Сервер говорит: "}
            pre { "{message:?}"}
            button { onclick: move |_| message.call("world".into(), 30), "Нажми меня!" }
        }
    });
}

#[get("/api/{name}/?age")]
async fn get_message(name: String, age: i32) -> Result<String> {
    Ok(format!("Привет {}, тебе {} лет!", name, age))
}
```

Ваш нативный код всё ещё может делать запросы к вашему бэкенду. Однако если вы развернёте свое приложение в production, вы можете заметить, что нативное приложение *не знает, куда делать запросы*.

В вебе запросы всегда делаются к текущему хосту origin. Например, запросы к этому эндпоинту делаются на `/api/dogs`:

```rust
#[get("/api/dogs")]
async fn get_message() -> Result<()> {
    ..
}
```

Десктоп и мобильные устройства не обслуживаются с конкретного URL, и поэтому не знают, к какому хосту делать запрос.

Чтобы задать конкретный URL сервера, вы должны вызвать `set_server_url` перед выполнением любых запросов:

```rust
fn main() {
    #[cfg(not(feature = "server"))]
    dioxus::fullstack::set_server_url("https://hot-dog.fly.dev");

    dioxus::launch(app);
}
```

Это гарантирует, что запросы всегда правильно объединяются с корректным хостом.

## Отключённые функции Fullstack

При использовании fullstack с нативными приложениями ряд функций и оптимизаций отключён. Нативные приложения обычно предназначены для использования офлайн, поэтому их рендеринг должен происходить полностью на клиенте. Архитектурно нативные приложения похожи на одностраничные приложения (SPA), где сначала загружается бандл, а *затем* делаются HTTP-запросы для загрузки контента.

Как таковые, ряд функций отключён:

- Нет контекста гидратации, и поэтому нет данных гидратации для гидратации страницы
- Приложение никогда не рендерится на сервере, пропуская код `#[cfg(feature = "server")]`
- Нет `FullstackContext` при рендеринге компонентов
- Потоковая передача HTML и SSG не имеют эффекта

Функционально это не изменит то, как вы создаёте свои приложения, но вы должны знать, что некоторый код может никогда не выполняться.


## Предпочитайте известные эндпоинты

Dioxus поддерживает два способа аннотирования серверных функций:

- Явно с помощью `#[get]`, `#[post]`, `#[delete]` и т. д.
- Анонимно с помощью `#[server]`

Когда вы используете макрос `#[server]`, путь эндпоинта может свободно меняться по мере обновления сигнатуры и тела эндпоинта. Если вы повторно развёртываете свой бэкенд, URL, которые работали ранее, не гарантированно будут существовать в будущем.


```rust
// ❌ этот эндпоинт генерирует `/api/do_it12nldkj2378jnakls`
#[server]
async fn do_it() -> Result<()> {
    //
}
```

Поскольку эндпоинт получает хэш, его имя уникально и может измениться по мере обновления его кода.

При использовании серверных функций с нативными клиентами мы настоятельно рекомендуем использовать аннотации `#[get]` / `#[post]`, поскольку они гарантируют стабильный эндпоинт.

```rust
// ✅ Этот эндпоинт стабилен
#[post("/api/do_it")]
async fn do_it() -> Result<()> {
    //
}
```

## Версионирование

Поскольку нативные клиенты распространяются как загружаемое ПО, они могут быть не всегда актуальны до последней версии вашего кода. Это может быть особенно сложно, когда вы хотите обновить сигнатуру эндпоинта.

```rust
// версия 1
#[post("/api/do_it")]
async fn do_it() -> Result<()> { /* */ }

// версия 2
// ❌ мы ломаем старых клиентов!
#[post("/api/do_it")]
async fn do_it(name: String) -> Result<()>  { /* */ }
```

Мы надеемся, эта проблема очевидна для вас — если вы повторно развёртываете свой бэкенд с ломающими изменениями, предыдущие клиенты сломаются!

Для обновления API мы рекомендуем один из двух вариантов:

- Использовать `Option<T>` для добавления новых полей
- Использовать версионирование `/api/v1`, `/api/v2/`

Для большинства обновлений API вы можете просто добавлять новые поля, делая новые значения опциональными с помощью `Option<T>`:

```rust
// версия 2
// ✅ Option<String> означает, что `name` не требуется
#[post("/api/do_it")]
async fn do_it(name: Option<String>) -> Result<()>  { /* */ }
```

Для изменений API, требующих гораздо больших изменений, мы рекомендуем использовать схему версионирования для создания различных версий API, доступных клиенту:

```rust
// Это находится на /api/v1/
#[post("/api/v1/do_it")]
async fn do_it() -> Result<()> { /* */ }

// Это находится на api/v2
#[post("/api/v2/do_it")]
async fn do_it(name: String) -> Result<()> { /* */ }
```

Создание различных версий API — обычная практика и помогает предотвратить поломку старых клиентов по мере обновления вашего приложения.

## Развёртывание

Вы можете развёртывать нативные fullstack-приложения точно так же, как и обычное веб-приложение. Серверные приложения всегда генерируют бинарник `server` и папку `/public/`. Нативные приложения будут генерировать бандл приложения (`.app`, `.ipa`, `.apk` и т. д.).

Вы можете распространять нативное приложение через магазин приложений или делая файл доступным для скачивания вашими пользователями.

Чтобы распространить сервер, просто загрузите его на хостинг-провайдер по вашему выбору. Пока вы установили `server_url` в нативном приложении, вы должны иметь возможность получать доступ к вашему бэкенду из нативного клиента.
