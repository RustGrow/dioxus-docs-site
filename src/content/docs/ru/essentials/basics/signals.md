# Реактивные сигналы

В Dioxus UI вашего приложения определяется как функция его текущего состояния. По мере изменения состояния компоненты и эффекты, которые зависят от этого состояния, будут автоматически перезапускаться. Реактивность автоматически *отслеживает* состояние и *выводит* новое состояние, упрощая создание больших приложений, которые эффективны и просты для понимания.

Dioxus предоставляет единственный источник изменяемого состояния: **Сигнал**.

## Состояние с помощью сигналов

В Dioxus изменяемое состояние хранится в сигналах. Сигналы — это *отслеживаемые* значения, которые автоматически обновляют *реактивные контексты*, которые наблюдают за ними. Они являются источником состояния, из которого выводится все остальное состояние. Сигналы модифицируются напрямую обработчиками событий в ответ на пользовательский ввод или асинхронно в futures.

Вы можете создать сигнал с помощью хука `use_signal`:

```rust
let mut signal = use_signal(|| 0);
```

Как только у вас есть сигнал, вы можете получить ссылку на внутреннее значение сигнала, вызвав `.read()`:

```rust
let mut signal = use_signal(|| 0);

// используйте `.read()` для доступа к внутреннему значению
let inner = signal.read();
```

Для сигналов, чье внутреннее значение может быть дешево клонируемым, вы также можете использовать "функциональный" синтаксис для получения прямого `Clone` значения.

```rust
let name = use_signal(|| "Bob".to_string());

// Вызовите сигнал как функцию
let inner = name();

// Или используйте `.cloned()`
let inner = name.cloned();
```

Наконец, вы можете установить значение сигнала с помощью метода `.set()` или получить изменяемую ссылку на внутреннее значение с помощью метода `.write()`:

```rust
// Установите значение сигнала
signal.set(1);

// получите изменяемую ссылку на внутреннее значение с помощью метода .write()
let mut value: &mut i32 = &mut signal.write();
*value += 1;
```

Простой компонент, который использует `.read()` и `.write()` для обновления своего собственного состояния с помощью сигналов, может выглядеть так:

```rust
fn Demo() -> Element {
    let mut count = use_signal(|| 0);

    // читаем текущее значение
    let current = count.read().clone();

    rsx! {
        button {
            onclick: move |_| *count.write() = current + 1,
            "Увеличить ({current})"
        }
    }
}
```

При присваивании значений вызову `.write()` обратите внимание, что мы используем [*оператор разыменования*](https://doc.rust-lang.org/std/ops/trait.DerefMut.html), который позволяет нам записывать значение непосредственно в изменяемую ссылку.

## Локальные Подписки

Сигналы подписывают компоненты только тогда, когда вы читаете из сигнала внутри этого компонента. Сигнал никогда не подпишет компонент, если данные читаются внутри future или обработчика события.

```rust
fn App() -> Element {
    // Поскольку сигнал никогда не читается в этом компоненте,
    // этот компонент не будет перезапускаться при изменении сигнала
    let mut signal = use_signal(|| 0);

    rsx! {
        button {
            onclick: move |_| {
                signal += 1;
            },
            "Увеличить"
        }
        for id in 0..10 {
            Child {
                signal,
            }
        }
    }
}

#[derive(Props, Clone, PartialEq)]
struct ChildProps {
    signal: Signal<usize>,
}

fn Child(props: ChildProps) -> Element {
    // Этот компонент читает из сигнала, поэтому при изменении сигнала он будет перезапущен
    rsx! {
        "{props.signal}"
    }
}
```

Поскольку подписки происходят при чтении (а не при создании) данных, вы можете передавать сигналы через обычный API контекста:

```rust
fn App() -> Element {
    // Поскольку сигнал никогда не читается в этом компоненте,
    // этот компонент не будет перезапускаться при изменении сигнала
    use_context_provider(|| Signal::new(0));

    rsx! {
        Child {}
    }
}

#[component]
fn Child() -> Element {
    let signal: Signal<i32> = use_context();
    // Этот компонент читает из сигнала, поэтому при изменении сигнала он будет перезапущен
    rsx! {
        "{signal}"
    }
}
```

## Эргономичные методы сигналов

В некоторых случаях оборачивание данных в сигналы может сделать доступ к внутреннему состоянию неуклюжим. Изменяемые сигналы реализуют два фундаментальных трейта: `Readable` и `Writable`. Эти трейты предоставляют ряд автоматических эргономичных улучшений.

- `Signal<T>` реализует `Display`, если `T` реализует `Display`
- `Signal<bool>` реализует `fn toggle()`
- `Signal<i32>` и другие числа реализуют математические операторы (+, -, / и т.д.)
- `Signal<T>`, где `T` реализует `IntoIterator`, реализует `.iter()`
- и многие другие!

Расширение `Display` позволяет использовать сигналы в выражениях форматирования:

```rust
let mut count = use_signal(|| 0);
rsx! { "Счетчик: {count}" }
```

Расширение toggle упрощает переключение булевых значений:
```rust
let mut enabled = use_signal(|| true);
rsx! {
    button {
        onclick: move |_| enabled.toggle(),
        if enabled() { "выключить" } else { "включить" }
    }
}
```

Математические операторы упрощают арифметические операции:

```rust
fn app() -> Element {
    let mut count = use_signal(|| 0);

    rsx! {
        h1 { "Счетчик high-five: {count}" }
        button { onclick: move |_| count += 1, "Вверх!" }
        button { onclick: move |_| count -= 1, "Вниз!" }
    }
}
```

Расширение итератора упрощает перебор коллекций:

```rust
fn app() -> Element {
    let names = use_signal(|| vec!["bob", "bill", "jane", "doe"]);

    rsx! {
        ul {
            for name in names.iter() {
                li { "привет {name}" }
            }
        }
    }
}
```

Обычно вы захотите использовать методы расширения, если только внутреннее состояние не реализует необходимые трейты. Доступно еще несколько методов, не перечисленных здесь, поэтому изучите документацию для получения дополнительной информации.

## ReadSignal и WriteSignal

Dioxus предоставляет две вариации базового типа Signal: `ReadSignal` и `WriteSignal`.

- **`ReadSignal`**: версия базового типа Signal только для чтения
- **`WriteSignal`**: версия базового типа Signal для чтения и записи, эквивалентная самому `Signal`

`ReadSignals` — это реактивные значения, реализующие трейт `Readable`. `WriteSignals` — это реактивные значения, реализующие трейт `Writable`.

Эти две вариации полезны при написании компонентов, которые должны быть обобщены по входным типам. Если компоненту нужен только метод `.read()` и его расширения, то он может принимать `ReadSignal` в качестве аргумента.


```rust
fn app() -> Element {
    let mut name: Signal<String> = use_signal(|| "abc".to_string());

    rsx! {
        // Макрос rsx автоматически преобразует Signal в ReadSignal
        Name { name }
    }
}

// Мы можем принимать всё, что реализует `Into<ReadSignal>`
#[component]
fn Name(name: ReadSignal<String>) -> Element {
    rsx! { "{name}" }
}
```

В Dioxus `Signal` — не единственный реактивный тип. Вся экосистема полна пользовательских реактивных типов. Сам Dioxus также предоставляет дополнительные реактивные типы, такие как `Memo` и `Resource`. Чтобы хорошо интегрироваться с более широкой экосистемой, лучше предпочитать использование `ReadSignal` и `WriteSignal` в ваших интерфейсах, а не конкретных реактивных типов.

Это гарантирует, что мы можем передавать как `Signal`, так и `Memo` в одну и ту же функцию:

```rust
let name: Signal<String> = use_signal(|| "abc".to_string());
let uppercase: Memo<String> = use_memo(move || name.to_uppercase());

rsx! {
    // Макрос rsx автоматически преобразует Signal в ReadSignal
    Name { name }
    // Макрос rsx автоматически преобразует Memo в ReadSignal
    Name { name: uppercase }
}

#[component]
fn Name(name: ReadSignal<String>) -> Element {
    rsx! { "{name}" }
}
```

## Реактивные Скоупы

**Реактивный Скоуп** — это блок кода Rust, который наблюдает за чтениями и записями реактивных значений. Когда `.write()` или `.set()` вызывается на сигнале, любые активные реактивные скоупы, отслеживающие этот сигнал, запускают callback в качестве побочного эффекта.

Простейший реактивный скоуп — это компонент. Во время рендера компонента они автоматически подписываются на сигналы, где вызывается `.read()`. Метод `.read()` может вызываться *неявно* во многих случаях — в частности, методы расширения, предоставляемые `Readable`, используют базовый метод `.read()` и, таким образом, *также* вносят вклад в текущий реактивный скоуп. Когда значение сигнала изменяется, компоненты ставят в очередь побочный эффект для повторного рендера компонента с помощью `dioxus::core::needs_update`.

```rust
let mut name = use_signal(|| "abc".to_string());

rsx! {
    // Явный вызов `.read()`
    {name.read().to_string()}

    // Неявный вызов через `Display`
    "{name}"
}
```

Если компонент не вызывает `.read()` на сигнале во время рендера, он не подписывается на значение этого сигнала. Это даёт нам "реактивность нулевой стоимости", когда мы можем свободно модифицировать значения сигналов, не беспокоясь о ненужных повторных рендерах. Если значение не наблюдается, оно не вызовет ненужных повторных рендеров.

```rust
let mut loading = use_signal(|| false);

rsx! {
    button {
        // Поскольку мы не используем "loading" в нашей разметке, компонент не будет перерисовываться!
        onclick: move |_| async move {
            if loading() {
                return;
            }
            loading.set(true);
            // .. делаем асинхронную работу
            loading.set(false);
        }
    }
}
```

Вызовы `.read()` обращаются к текущему реактивному скоупу, добавляя этот скоуп в список подписчиков сигнала с побочным эффектом, который запускается при изменении сигнала. Для компонентов эта логика заставляет компонент ставить в очередь побочный эффект повторного рендера.

![Компонентные эффекты](/assets/07/component-effect.png)

Существуют и другие применения реактивных скоупов, помимо повторных рендеров компонентов. Хуки, такие как `use_effect`, `use_memo` и `use_resource`, реализуют функциональность, используя реактивный скоуп, который существует *вне* жизненного цикла рендеринга.

## Автоматическое Батчинг

Все встроенные хуки выполняют батчинг обновлений, если возможно. Вместо немедленного запуска эффектов вызовы `.write()` ставят эффект в очередь перед следующим "шагом" вашего приложения. Рантайм постарается дождаться завершения всех записей в текущем шаге перед запуском каких-либо эффектов. Это обеспечивает автоматический батчинг вызовов `.write()`, что важно как для производительности, так и для консистентности UI.

Благодаря батчингу вызовов `.write()`, Dioxus гарантирует, что наш пример UI всегда отображает одно из двух состояний:
- **"loading?: false -> Complete"**
- **"loading?: true -> Loading"**

```rust
let mut loading = use_signal(|| false);
let mut text = use_signal(|| "Complete!");

rsx! {
    button {
        onclick: move |_| async move {
            // эти записи батчатся и побочные эффекты дедуплицируются
            text.set("Loading");
            loading.set(true);

            // ожидание future позволяет рантайму продолжить
            do_async_work().await

            // эти записи также батчатся — ставится только один повторный рендер
            text.set("Complete!");
            loading.set(false);
        },
        "loading?: {loading:?} -> {text}"
    }
}
```

Dioxus использует границы `await` как барьеры между шагами. Если состояние модифицируется во время шага, Dioxus предпочитает сначала отрисовать новый UI, прежде чем опрашивать дополнительные futures. Это гарантирует, что изменения применяются как можно быстрее, а состояния ожидания не пропускаются.

Хотя Dioxus старается батчить записи, он предпочитает консистентное состояние батчингу, когда эти два аспекта конфликтуют. Если вы прочитаете результат мемо сразу после записи в сигнал, от которого он зависит, мемо будет немедленно переоценён, чтобы гарантировать, что вы получите самое актуальное значение. Это гарантирует, что мемо всегда эквивалентен прямому запуску функции мемо.

```rust
let mut count = use_signal(|| 0);
let double = use_memo(move || count() * 2);

rsx! {
    button {
        onclick: move |_| async move {
            // Это ставит в очередь повторный запуск мемо и помечает его как грязный
            count += 1;
            // Это принуждает мемо к немедленной переоценке
            println!("double is now: {}", double());
        },
        "удвоено: {double}"
    }
}
```

## Сигналы Заимствуются во Время Выполнения

В Rust типы ссылок `&T` и `&mut T` статически утверждают, что базовое значение либо неизменяемо, либо изменяемо *во время компиляции*. Это утверждение даёт ряд гарантий, позволяя Rust генерировать быстрый и корректный код.

К сожалению, эти статические утверждения плохо сочетаются с асинхронными фоновыми задачами. Если наш обработчик `onclick` порождает долго выполняющийся Future, который захватывает `&mut T`, мы не можем безопасно обрабатывать *никакие другие* события, пока этот Future не завершится:

![Изменяемость во времени](/assets/07/mutable-diagram.png)

Иногда наши UI могут быть очень конкурентными. *Есть* способы переориентировать, как мы конкурентно обращаемся к состоянию, которые совместимы со статическими утверждениями изменяемости Rust — к сожалению, они не просты в программировании.

Вместо этого сигналы предоставляют метод `.write()`, который проверяет *во время выполнения*, безопасен ли доступ к значению. Если вы не будете осторожны, вы можете комбинировать `.read()` и `.write()` в одном скоупе, что приведёт к ошибке заимствования во время выполнения (панике).

Это чаще всего встречается при удержании ссылок `.read()` или `.write()` через точки await:

```rust
let mut state = use_signal(|| 0);

rsx! {
    button {
        // Быстрое нажатие этой кнопки вызовет несколько активных вызовов `.write()`
        onclick: move |_| async move {
            let mut writer = state.write();
            sleep(Duration::from_millis(1000)).await;
            *writer = 10;
        }
    }
}
```

К счастью, этот код не проходит `cargo clippy`, потому что тип `writer` не должен удерживаться через точку await.

К счастью, сигналы защищают от "тривиального" случая, потому что метод `.write()` принимает `&mut Signal`. Пока guard `.write()` активен в скоупе (блоке), никакие другие guards `.read()` или `.write()` не могут удерживаться:

```rust
let mut state = use_signal(|| 0);

rsx! {
    button {
        // rust предотвращает компиляцию этого кода, поскольку `.write()` принимает `&mut T`
        onclick: move |_| {
            let cur = state.read();
            *state.write() = *cur + 1;
        }
    }
}
```

Мы получаем очень хорошее сообщение об ошибке от компилятора Rust, объясняющее, почему этот код не компилируется:

```text
error[E0502]: cannot borrow `state` as mutable because it is also borrowed as immutable
  --> examples/readme.rs:22:18
   |
21 |                 let cur = state.read();
   |                           ----- immutable borrow occurs here
22 |                 *state.write() = *cur + 1;
   |                  ^^^^^^^^^^^^^ mutable borrow occurs here
23 |             }
   |             - immutable borrow might be used here, when `cur` is dropped and runs the destructor for type `GenerationalRef<Ref<'_, i32>>`
```

Если мы *действительно* хотим читать и писать в одном скоупе, нам нужно разместить наши операции в правильном порядке так, чтобы guards `.read()` и `.write()` не перекрывались. Обычно это делается путём получения owned значения из операции `.read()`, которое будет использоваться в операции `.write()`.

```rust
let cur = state.read().clone(); // вызов `.clone()` немедленно освобождает guard `.read()`.
*state.write() = *cur + 1;
```

Обратите внимание, что Rust автоматически удаляет элементы *в конце* скоупа, если они не удалены вручную раньше. Мы можем использовать guard `.read()`, если он удалён до вызова `.write()`.

Это делается либо путём создания нового, более короткого скоупа для доступа к guard `.read()` —
```rust
// Guard `.read()` живет только в более коротком скоупе
let next = {
    let cur = state.read();
    println!("{cur}");
    cur.clone() + 1
};

// мы можем присвоить `state` значение `next`, поскольку `next` не ссылается на `.read()`.
*state.write() = next;
```

или просто путём вызова `drop()` на guard
```rust
let cur1 = state.read();
let cur2 = *cur1 + 1;
drop(cur1); // раннее удаление гарантирует, что мы можем безопасно выполнить `.write()` на сигнале
*state.write() = cur2 + 1;
```

В очень продвинутых сценариях использования вы можете сделать копию сигнала или использовать метод `read_unchecked` для ослабления правил заимствования:

```rust
match result.read_unchecked().as_ref() {
    Ok(resp) => rsx! { "success! {resp}" }
    Err(err) => rsx! { "err: {err:?}" },
}
```

> Rust 2021 имел проблемы с `.read()` в match-выражениях, тогда как Rust 2024 исправляет эту проблему, то есть вам больше не нужно использовать `read_unchecked`

Хотя это может показаться пугающим или подверженным ошибкам, вы *очень редко* столкнётесь с этими проблемами при создании приложений. Guards `.read()` и `.write()` уважают правила владения Rust в пределах данного скоупа, а конкурентные скоупы защищены [линтом Clippy `await_holding_refcell_ref`](https://rust-lang.github.io/rust-clippy/master/index.html#await_holding_refcell_ref).

### Сигналы в Асинхронном Коде

Поскольку сигналы проверяют заимствования во время выполнения, вам нужно быть осторожным при чтении и записи в сигналы внутри асинхронного кода. Если вы удерживаете чтение или запись сигнала через точку await, это чтение или запись может оставаться открытым, пока выполняются другие части вашего приложения:

```rust no_run
async fn double_me_async(value: &mut u32) {
    sleep(100).await;
    *value *= 2;
}
let mut signal = use_signal(|| 0);

use_future(move || async move {
    // Не удерживайте чтения или записи через точки await
    let mut write = signal.write();
    // Пока future ожидает завершения асинхронной работы, запись будет открыта
    double_me_async(&mut write).await;
});

rsx!{
    // Это чтение может вызвать панику, потому что запись всё ещё активна
    "{signal}"
};
```

Вместо удержания чтения или записи через точку await, вы можете клонировать необходимые значения из сигнала, а затем установить результат, когда асинхронная работа завершится:

```rust no_run
async fn double_me_async(value: u32) -> u32 {
    sleep(100).await;
    value * 2
}
let mut signal = use_signal(|| 0);

use_future(move || async move {
    // Клонируем значение из сигнала
    let current_value = signal();
    // Выполняем асинхронную работу
    let new_value = double_me_async(current_value).await;
    // Устанавливаем сигнал в новое значение
    signal.set(new_value);
});

rsx! {
    // Это чтение не вызовет панику, потому что запись никогда не удерживается через точку await
    "{signal}"
};
```

## Сигналы реализуют `Copy`

Если вы использовали Rust для создания других проектов — таких как веб-сервер или инструмент командной строки — вы могли столкнуться с ситуациями с замыканиями, потоками и асинхронными задачами, которые требовали `Arc` или `Rc`, чтобы удовлетворить borrow checker.

![Конкурентный доступ](/assets/07/concurrent-arc.png)

Если наши данные используются в нескольких параллельных потоках, или даже просто хранятся в callback, нам может потребоваться обернуть их в умный указатель `Arc` или `Rc` и вызвать `.clone()`. Это может привести к громоздкому коду, где мы постоянно вызываем `.clone()`, чтобы передавать данные в callbacks и асинхронные задачи.

```rust
let state = Arc::new(123);

// поток 1
std::thread::spawn({
    let state = state.clone();
    move |_| println!("{state:?}"),
})

// поток 2
std::thread::spawn({
    let state = state.clone();
    move |_| println!("{state:?}"),
})
```

К сожалению, код UI постоянно сталкивается с этой проблемой — **именно поэтому Rust не имеет отличной репутации для создания GUI приложений**!

Чтобы решить это, мы создали [крейт generational-box](https://crates.io/crates/generational-box), который предоставляет тип `GenerationalBox`, реализующий [трейт Rust `Copy`](https://doc.rust-lang.org/std/marker/trait.Copy.html). Трейт `Copy` очень важен: Rust автоматически копирует типы `Copy` (при необходимости) на границах скоупов.

```rust
let state = GenerationalBox::new(123);

// ключевое слово `move` автоматически копирует GenerationalBox!
std::thread::spawn(move |_| println!("{state:?}"));

// мы можем легко делиться между потоками без шума `.clone()`
std::thread::spawn(move |_| println!("{state:?}"));
```

Вместо копирования базового значения, `GenerationalBox` просто копирует *handle* к значению. Этот handle по сути является runtime-проверенным умным указателем. Доступ к содержимому сигнала не так эффективен, как прямое чтение указателя — есть дополнительная косвенная адресация и блокировка — но мы ожидаем, что большинство кода не будет ограничено чтением содержимого `GenerationalBox`.

Сигналы Dioxus построены непосредственно на основе `GenerationalBox`. Они используют ту же семантику `Copy` и эргономику, но с теми же компромиссами.

## Сигналы Уничтожаются

То, что сигналы реализуют `Copy`, является огромным выигрышем для эргономики. Однако есть компромисс. Тип `GenerationalBox` не имеет автоматической поддержки [RAII](https://doc.rust-lang.org/rust-by-example/scope/raii.html). Это означает, что когда `GenerationalBox` удаляется, его ресурсы **не освобождаются немедленно**. Может быть сложно правильно использовать `GenerationalBox` напрямую. Dioxus управляет *жизненным циклом ресурсов*, очищая ресурсы с помощью *жизненного цикла компонентов*.

Тип Signal построен на `GenerationalBox`. Когда вы вызываете `use_signal`, мы автоматически:

- Вызываем `Signal::new()`
- Регистрируем `signal.dispose()` в `on_drop` компонента

Когда компонент размонтируется, его хуки удаляются. Когда вы создаёте сигналы в компоненте, каждый сигнал регистрируется с "владельцем" сигнала в этом компоненте. Когда компонент размонтируется, владелец удаляется, и в своей реализации `Drop` вызывает `.dispose()` для всех сигналов, созданных в его скоупе.

По сути, мы соединили метод `.dispose()` сигналов с размонтированием компонента.

Поскольку сигнал уничтожается при размонтировании компонента, чтение его после этого вызовет runtime-панику. Это очень редко случается на практике, но *возможно*, если вы "сохраняете" сигнал в компоненте выше по дереву. Это нарушало бы столп однонаправленного потока данных реактивности, но технически возможно.

![Конкурентный доступ](/assets/07/use-after-free.png)

Чтение сигнала после его уничтожения похоже на баг "use-after-free" с указателями, но чтение сигнала *не является* неопределённым поведением. В режиме отладки сигнал будет поднят к своему читателю, и вы получите предупреждение в логах о том, что сигнал читается после уничтожения.

Похожая проблема может возникнуть, когда вы вызываете `Signal::new()` напрямую. Dioxus создаёт неявного владельца сигнала, которым владеет текущий компонент. Содержимое этого сигнала будет удалено только при размонтировании текущего компонента. Вызов `Signal::new()` может привести к неограниченному использованию памяти, пока компонент не удалён. Это редко встречается в обычном прикладном коде, но может возникнуть при разработке библиотек.

```rust
let mut users = use_signal(|| vec![]);

rsx! {
    button {
        // базовые строки не будут удалены, пока компонент не размонтирован, или вы не вызовете `.dispose()` вручную
        onclick: move |_| {
            users.write().push(Signal::new("bob".to_string()));
        },
        "Добавить нового пользователя"
    }
}
```

При отображении сигналов или создании их на лету лучше предпочитать встроенные методы и реактивные коллекции.

### Не Передавайте Сигналы Вверх по Дереву Компонентов

Время жизни сигнала привязано к времени жизни компонента, в котором он был создан. Если вы удалите компонент, создавший сигнал, сигнал тоже будет удалён. Вы можете столкнуться с этим, если попытаетесь передать сигнал из дочернего компонента в родительский и удалить дочерний компонент. Чтобы избежать этого, вы можете создать сигнал выше в дереве компонентов, использовать глобальные сигналы или создать сигнал в определённом скоупе с помощью `Signal::new_in_scope`.

```rust
fn MyComponent() -> Element {
    let child_signal = use_signal(|| None);

    rsx! {
        IncrementButton {
            child_signal
        }
    }
}

#[component]
fn IncrementButton(mut child_signal: Signal<Option<Signal<i32>>>) -> Element {
    let signal_owned_by_child = use_signal(|| 0);
    // Не делайте так: это может вызвать проблемы, если дочерний компонент будет удалён
    child_signal.set(Some(signal_owned_by_child));

    todo!()
}
```

## Эффекты, Мемо и другое

Сигналы — это лишь одна часть системы реактивности Dioxus. Хуки, такие как `use_effect` и `use_memo`, способны изолировать свои реактивные скоупы только для callbacks и futures. Это означает, что `.read()` и `.write()` в этих скоупах не ставят побочные эффекты повторного рендера в их содержащем компоненте.

Мы рассмотрим эти хуки более подробно в [следующей главе](./effects.md).
