# Рендеринг списков

## Итераторы и встроенные `for`

В главе [Условный рендеринг](./conditional.md) мы показали, как Rust-выражения становятся динамическими узлами в блоках RSX.

Любой итератор, возвращающий `Element` или объект, реализующий `IntoVnode`, может использоваться внутри блоков RSX для рендеринга списков:

```rust
rsx! {
    // отображение существующих итераторов
    {(0..10).map(|idx| rsx! { "item {idx}" })}

    // или вызов .iter()
    {users.iter().map(|user| rsx!{ User { id: user.id } })}
}
```

Dioxus предоставляет небольшой синтаксический сахар, чтобы использование итераторов было чуть приятнее. Вместо оборачивания итератора в выражение, можно переместить его во встроенный блок `for`:

```rust
rsx! {
    for idx in 0..10 {
        "Item {idx}"
    }

    for user in users.iter() {
        User { id: user.id }
    }
}
```

Как и встроенные блоки `if`, тела циклов `for` являются RSX, а не Rust-выражениями. Если нужно создать временные переменные или выполнить дополнительные вычисления во время итерации, можно использовать встроенное выражение:

```rust
rsx! {
    for user in users.iter() {
        {
            let id = user.id();
            rsx! {
                User { id }
            }
        }
    }
}
```

Если мы используем итераторы вместе с типами-обёртками, такими как `Signal<T>`, сначала нужно вызвать `.iter()`:


```rust
let mut items = use_signal(|| vec!["Hello", "Dioxus"]);

    rsx! {
        ul {
            for item in items.iter() {
                li { "{item}" }
            }
        }
    }
```


## Ключи обязательны

Каждый элемент в списке должен иметь уникальное значение, стабильное между рендерами, называемое ключом (key). Ключи используются для определения того, как элементы перемещаются между рендерами. Без ключей легко случайно потерять или переместить состояние при изменении порядка элементов в списке. Мы можем добавить ключи к элементам списка, используя атрибут `key`:

```rust
let mut items = use_signal(|| vec!["Hello", "Dioxus"]);

    rsx! {
        ul {
            for item in items.iter() {
                li { key: "{item}", "{item}" }
            }
        }
    }
```


Подходящий ключ обычно можно найти прямо в вашем состоянии. Большинство данных в интерфейсе имеет какой-то уникальный идентификатор, который можно использовать для различения от других записей в коллекции. Например, у пользователей обычно есть уникальный ID, у временных выборок — уникальная временная метка, а у писем — уникальный адрес отправителя.

```rust
rsx! {
    for user in users {
        div { key: "{user.id}", "{user.name}" }
    }
}
```

Обратите внимание, что некоторые поля могут *казаться* подходящим уникальным ID, но таковыми не являются. Два пользователя могут иметь одинаковое имя, две точки данных могут иметь одинаковую временную метку, или не у каждой записи могут быть нужные данные. В таких случаях мы рекомендуем создавать уникальный ID для каждого элемента на основе глобального счётчика "поколений". Обычно его предоставляет база данных, но можно также использовать состояние для управления:

```rust
let mut generation = use_signal(|| 0);
let mut items = use_signal(|| vec![]);

let mut add_item = move |name| {
    let id = generation();
    generation.set(id + 1);
    items.write().push(Item { id, name })
};

rsx! {
    for item in items.iter() {
        div { key: "{item.id}", "{item.name}" }
    }
    ...
}
```

*Худший* ключ для использования — индекс элемента в коллекции. Индекс элемента будет меняться при изменении списка и почти наверняка вызовет либо проблемы с производительностью, либо потерю состояния в компонентах.

```rust
// ❌ не делайте так!
rsx! {
    for (idx, user) in users.iter().enumerate() {
        div { key: "{idx}", "{user.name}" }
    }
}
```

## Компонент Fragment

В некоторых случаях ваши итераторы могут возвращать несколько корневых элементов. Это не даёт нам хорошего места для размещения ключа. RSX автоматически использует ключ первого элемента как ключ итератора, если он существует:

```rust
rsx! {
    for item in items.iter() {
        h1 { key: "{item.id}", "{item.name}" }
        p { "content" }
    }
}
```

Если нет простого способа прикрепить ключ к первому элементу, можно использовать компонент `Fragment`, чтобы обернуть элементы и дать ключ ему:

```rust
rsx! {
    for item in items.iter() {
        Fragment {
            key: "{item.id}",
            for child in item.children.iter() {
                div { "{child}" }
            }
        }
    }
}
```

Компонент `Fragment` ничем не примечателен. Это просто компонент, который передаёт своих детей как своё тело. Однако RSX видит его как допустимый синтаксис элемента и может правильно назначить ключ.

```rust
#[component]
fn Fragment(children: Element) -> Element {
    children
}
```


## Заимствованное состояние

При рендеринге списков может потребоваться заимствовать некоторое содержимое данных в дочерние компоненты. Общий контейнер Dioxus, Signal, не способен предоставлять ссылки дочерним компонентам.

```rust
let items = use_signal(|| vec![]);

rsx! {
    for item in items.iter() {
        Card {
            // ❌ невозможно передать ссылку дочернему компоненту.
            content: item.name.as_str()
        }
    }
}
```

Хотя ранние версии Dioxus позволяли передавать ссылки, мы в итоге отключили эту функцию, так как она опиралась на некорректную семантику Rust. Вместо этого мы рекомендуем три стратегии:

- Использовать владеемые данные и `clone`, если это дёшево
- Передавать в компонент коллекцию *и* индекс
- Использовать `Store` для предоставления реактивной ссылки на часть данных внутри коллекции

Stores позволяют эффективно углубляться в реактивное состояние. Они подробно рассмотрены в главе [Stores](../basics/collections.md), но вот краткий предпросмотр их использования:

```rust
fn app() -> Element {
    let mut vec = use_store(|| vec![]);

    rsx! {
        div {
            // Итерация по store предоставляет ссылки на реактивные элементы внутри store
            // без их клонирования.
            for count in vec.iter() {
                Child { count }
            }
        }
    }
}

#[component]
fn Child(count: ReadSignal<i32>) -> Element {
    rsx! { "{count}" }
}
```

Для сложных приложений мы рекомендуем строить систему вокруг глобального контекста или использовать Store.
