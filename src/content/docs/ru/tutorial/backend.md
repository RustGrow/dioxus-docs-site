# Добавление бэкенда

Dioxus — это _фулстек_ фреймворк, позволяющий вам бесшовно строить фронтенд вместе с бэкендом.

Мы предоставляем ряд утилит, таких как _Серверные функции_, _Server Futures_ и _Server State_ для интеграции в ваши приложения. В этой главе мы рассмотрим загрузку и сохранение состояния на наш бэкенд с помощью _Серверных функций_. Для подробного руководства по фулстеку ознакомьтесь с [руководством по фулстеку](../essentials/fullstack/index.md).

## Включение фулстека

Прежде чем мы сможем начать использовать серверные функции, нам нужно включить фичу "fullstack" на Dioxus в нашем Cargo.toml.

```toml
[dependencies]
dioxus = { version = "0.7.0", features = ["fullstack"] }
```

Нам также нужно добавить фичу "server" в фичи нашего приложения в Cargo.toml и удалить целевую платформу web по умолчанию.

```toml
[features]
default = [] # <----- удалите целевую платформу web по умолчанию
web = ["dioxus/web"]
desktop = ["dioxus/desktop"]
mobile = ["dioxus/mobile"]
server = ["dioxus/server"] # <----- добавьте эту дополнительную цель
```

Если вы выбрали *yes* на вопрос "use fullstack?" при создании вашего приложения, у вас уже все настроено!

> 📣 К сожалению, `dx` не знает, как горячим способом перезагрузить это изменение, поэтому нам нужно будет перезапустить dev-сервер.

Теперь вместо запуска `dx serve` вам нужно запускать с ручной платформой с помощью `dx serve --web`. Дайте вашему приложению немного времени на сборку и убедитесь, что фича "fullstack" включена в дашборде.

## Серверные функции: встроенная RPC-система

Dioxus интегрируется с крейтом [axum](https://crates.io/crates/axum) для предоставления простой встроенной системы коммуникации для ваших приложений. Серверные функции упрощают создание бэкенда вашего приложения с помощью простых Rust-функций. Серверные функции — это `async` функции, аннотированные процедурным макросом (вроде post/get).

Типичная серверная функция выглядит так:

```rust
#[post("/api/save_dog")]
async fn save_dog(image: String) -> Result<()> {
    Ok(())
}
```

Каждая серверная функция — это async-функция, которая принимает некоторые параметры и возвращает `Result<()>`. Всякий раз, когда клиент вызывает серверную функцию, он отправляет HTTP-запрос на соответствующий endpoint на сервере. Параметры серверной функции сериализуются как тело HTTP-запроса. В результате каждый аргумент должен быть сериализуемым.

На клиенте серверная функция разворачивается в вызов `reqwest`:

```rust
// на клиенте:
async fn save_dog(image: String) -> Result<()> {
    reqwest::Client::new()
        .post("http://localhost:8080/api/save_dog")
        .json(&image)
        .send()
        .await?;
    Ok(())
}
```

На сервере серверная функция разворачивается в [axum](https://github.com/tokio-rs/axum) handler:

```rust
// на сервере:
struct SaveDogArgs {
    image: String,
}

async fn save_dog(Json(args): Json<SaveDogArgs>) -> Result<()> {
    Ok(())
}
```

При вызове `dioxus::launch` серверные функции автоматически регистрируются для вас и настраиваются как Axum router.

В некоторых случаях функция `dioxus::launch` может быть слишком ограничивающей для вашего use-case на сервере. Dioxus предоставляет альтернативную точку входа для вашего приложения на сервере с помощью `dioxus::serve`. Это позволяет вам возвращать Axum router, сохраняя при этом горячую перезагрузку, логирование и devtools, подключенные автоматически.

```rust
fn main() {
    #[cfg(not(feature = "server"))]
    dioxus::launch(App);

    #[cfg(feature = "server")]
    dioxus::serve(|| async move {
        // Создаём новый axum router для нашего Dioxus-приложения
        let router = dioxus::server::router(App);

        // .. настраиваем его как хотим ..

        // И возвращаем его
        Ok(router)
    })
}
```

## Разделение Клиент/Сервер

Когда Dioxus собирает ваши фулстек-приложения, он фактически создаёт два отдельных приложения: сервер и клиент. Чтобы добиться этого, `dx` передаёт разные фичи каждой сборке.

- Клиент собирается с `--features web`
- Сервер собирается с `--features server`

![Server Client Split](/assets/06_docs/server_split.png)

При встраивании серверного кода в наши приложения нам нужно быть осторожными относительно того, какой код компилируется. Тело серверной функции предназначено для выполнения *только на сервере* — не на клиенте. Любой код, настроенный фичей `"server"`, не будет присутствовать в финальном приложении. И наоборот, любой код, не настроенный фичей `"server"`, *будет* включён в финальное приложение.

```rust
// ❌ это утечёт ваш DB_PASSWORD в клиентское приложение!
static DB_PASSWORD: &str = "1234";

#[post("/api/do_thing")]
async fn DoThing() -> Result<()> {
    connect_to_db(DB_PASSWORD).await
    // ...
}
```

Вместо этого мы рекомендуем размещать код, предназначенный только для сервера, в модулях, настроенных для фичи `"server"`.

```rust
// ✅ код в этом модуле может быть доступен только на сервере
#[cfg(feature = "server")]
mod server_utils {
    pub static DB_PASSWORD: &str = "1234";
}
```

В дополнение к фиче "server", Dioxus ожидает фичу клиентского рендеринга, такую как "web" или "desktop". Некоторые библиотеки, такие как web-sys, работают только при запуске в браузере, поэтому убедитесь, что не запускаете специфичный клиентский код в ваших серверных функциях или до вашего `launch`. Вы можете разместить код только для клиента под конфигурацией для клиентской целевой фичи, такой как "web".

```rust
fn main() {
    // ❌ попытка использовать web_sys на сервере вызовет панику!
    let window = web_sys::window();

    // ..

    dioxus::launch(App);
}
```

## Управление зависимостями

Некоторые зависимости, такие как [Tokio](https://github.com/tokio-rs/tokio), компилируются корректно только при таргетировании на нативные платформы. Другие зависимости, такие как [jni-sys](https://github.com/jni-rs/jni-sys), работают корректно только при запуске на конкретной платформе. В этих случаях вы захотите убедиться, что эти зависимости компилируются только когда включена конкретная фича. Для этого мы можем использовать флаг `optional` Rust для зависимостей в нашем Cargo.toml.

```toml
[dependencies]
tokio = { version = "1", optional = true }

[features]
default = []
server = ["dep:tokio"]
```

В конце концов, если ваш проект станет достаточно большим, вы можете захотеть вынести ваши серверные функции в собственный крейт для использования в разных приложениях. Мы бы создали крейт `server` в нашем воркспейсе:

```sh
├── Cargo.toml
└── crates
    ├── dashboard
    ├── marketplace
    └── server
```

А затем импортировали бы серверные функции в наше приложение, отключив их фичу `"server"`.

```toml
[dependencies]
server = { workspace = true, default-features = false }
```

Мы предоставляем более подробное руководство о деталях управления зависимостями между сервером и клиентом [здесь](../essentials/fullstack/project_setup.md).

## Наша серверная функция HotDog

Вернёмся к нашему приложению HotDog, давайте создадим новую серверную функцию, которая сохраняет нашу любимую собаку в файл с названием `dogs.txt`. В production вы бы хотели использовать правильную базу данных, как описано в [следующей главе](databases.md), но пока что мы используем простой файл для тестирования.

```rust
// Экспонируем endpoint `save_dog` на нашем сервере, принимающий параметр "image"
#[post("/api/save_dog")]
async fn save_dog(image: String) -> Result<()> {
    use std::io::Write;

    // Открываем файл `dogs.txt` в режиме только-добавление, создавая его, если он не существует;
    let mut file = std::fs::OpenOptions::new()
        .write(true)
        .append(true)
        .create(true)
        .open("dogs.txt")
        .unwrap();

    // И затем записываем новую строку с URL изображения
    file.write_fmt(format_args!("{image}\n"));

    Ok(())
}
```

### Вызов серверной функции

Теперь в нашем клиентском коде мы можем вызвать серверную функцию.

```rust
fn DogView() -> Element {
    let mut img_src = use_resource(snipped!());

    // ...
    rsx! {
        // ...
        div { id: "buttons",
            // ...
            button {
                id: "save",
                onclick: move |_| async move {
                    let current = img_src.cloned().unwrap();
                    img_src.restart();
                    _ = save_dog(current).await;
                },

                "save!"
            }
        }
    }
}
```

Вау, наше приложение действительно обретает форму!
